# 05. Dev Roadmap — от MVP до интеграций

> Порядок этапов рассчитан на выполнение AI-агентом разработки (Antigravity / Cursor / Claude Code)
> пошагово, с проверкой результата после каждого этапа перед переходом к следующему.

## Этап 0 — Подготовка репозитория (перед этапом 1)

- Инициализировать монорепо: `backend/`, `frontend/`, `docs/` (эта папка), `infra/`.
- Стек по умолчанию (если не переопределено заказчиком): backend — Node.js/NestJS или Python/FastAPI + PostgreSQL + Prisma/SQLAlchemy; frontend — React + TypeScript + Vite; очереди — BullMQ/Celery для async jobs (recalc плана, batch overdue).
- CI: lint + typecheck + test на каждый PR.

---

## Этап 1 — DB / ORM (Data Layer)

**Вход:** `docs/01_DATA_MODEL.md`
**Выход:** миграции БД, ORM-модели, seed-справочники (категории материалов, регионы, роли).

Шаги:
1. Создать схему БД по всем таблицам из `01_DATA_MODEL.md` (articles, materials, bom_items, price_history, customers, orders, order_lines, payment_documents, payments, acceptance_acts, material_stock_movements, finished_goods_movements, min_stock_levels, production_plan_items, production_stages, work_calendar_days, employees, users, roles, audit_log).
2. Настроить FK-связи и индексы по полям поиска (`article_code`, `order_number`, `bin_iin`, `period_key`).
3. Сгенерировать `work_calendar_days` на текущий и следующий год (скрипт-сидер, учёт выходных/праздников РК).
4. Написать unit-тесты на констрейнты (UNIQUE, NOT NULL, FK).

**Критерий готовности:** миграции применяются с нуля без ошибок, seed-скрипт создаёт базовые справочники, все таблицы из `01_DATA_MODEL.md` покрыты.

## Этап 2 — Бизнес-логика (Service Layer)

**Вход:** `docs/02_BUSINESS_LOGIC.md`
**Выход:** сервисы пересчёта, event-обработчики, state machine заказа, scheduled jobs.

Шаги:
1. Реализовать формулы п. 2.1–2.11 как чистые функции/сервисы (без привязки к HTTP-слою — тестируемые изолированно).
2. Реализовать event-driven пересчёт (см. таблицу в разделе 1 `02_BUSINESS_LOGIC.md`): `OrderLineCreated`, `StockMovementPosted`, `PriceChanged`, `BomChanged`.
3. Реализовать state machine `Order.status` с валидацией переходов (раздел 3 документа).
4. Реализовать scheduled job пересчёта `overdue_days` (ежедневно) и job уведомлений о просрочке (заготовка под MVP quick-win из старого ТЗ, раздел 5.2).
5. Unit-тесты на каждую формулу (сверка с примерами значений из исходного Excel, если есть тестовые данные).

**Критерий готовности:** 100% формул из `02_BUSINESS_LOGIC.md` покрыты тестами; state machine отклоняет недопустимые переходы (`409`).

## Этап 3 — Backend API

**Вход:** `docs/03_API_SPECIFICATION.md`, `docs/04_ROLES_PERMISSIONS.md`
**Выход:** REST API v1, аутентификация, RBAC-мидлвары, Swagger/OpenAPI-документация.

Шаги:
1. Реализовать все эндпоинты раздела 1–4 из `03_API_SPECIFICATION.md`.
2. Подключить JWT-аутентификацию и RBAC-guard по матрице из `04_ROLES_PERMISSIONS.md` (каждый эндпоинт помечен требуемой ролью/правом).
3. Подключить audit log middleware — автоматическая запись изменений на все `POST/PATCH/DELETE`.
4. Реализовать пагинацию, фильтры, обработку ошибок по единому формату.
5. Сгенерировать OpenAPI-спецификацию из кода (swagger-decorators/pydantic) — сверить с `03_API_SPECIFICATION.md` на расхождения.
6. Интеграционные тесты (Supertest/pytest) на ключевые сценарии: создание заказа → смена статуса → движение склада → закрытие заказа.

**Критерий готовности:** все эндпоинты отвечают согласно спецификации, RBAC блокирует запрещённые действия `403`, есть автотесты на основной happy path.

## Этап 4 — Frontend UI

**Вход:** результаты старого ТЗ раздел 3 (роли/UX), `03_API_SPECIFICATION.md`

Шаги:
1. Каркас приложения: авторизация, роутинг по ролям, лейаут (сайдбар — модули: Заказы, План, Склад, Финансы, Справочники, Дашборд).
2. Реестр заказов (таблица + фильтры + модалка создания/редактирования заказа, мастер по шагам: клиент → позиции → оплата → план вывоза).
3. Экран производственного плана: таблица агрегатов по неделям/месяцам/кварталам + Гант-визуализация с drag-n-drop переноса сроков.
4. Канбан-доска этапов производства (`production_stages`) с drag-n-drop между колонками, фото брака.
5. Склад: экраны прихода/расхода ТМЦ и ГП, заявка на закупку с фильтрами по группе материала.
6. Финансы: реестр ДО, платежи, дебиторская задолженность.
7. Дашборд руководителя: KPI-карточки (план/факт, загрузка цеха, дебиторка, остатки vs. норматив).
8. Явное визуальное разделение полей Input/Calculated (readonly-стиль для расчётных полей).

**Критерий готовности:** все экраны покрывают сценарии из матрицы ролей (`04_ROLES_PERMISSIONS.md`), UI скрывает недоступные по роли действия (не просто дизейблит кнопку — сервер тоже должен отклонять).

## Этап 5 — Интеграции (Bitrix24 / 1С / WMS / Telegram)

**Вход:** старое ТЗ раздел 4 (Integration Readiness), `03_API_SPECIFICATION.md` раздел 5

Шаги:
1. Реализовать приём вебхуков `/webhooks/bitrix/deal-updated`, `/webhooks/1c/payment-posted`, `/webhooks/1c/stock-updated`, `/webhooks/telegram/stage-confirmed` с проверкой подписи и идемпотентностью.
2. Реализовать исходящие уведомления в Bitrix24 (статус готовности, дата отгрузки) и в 1С (факт выпуска ГП, списание сырья).
3. Telegram-бот для мастера цеха: подтверждение этапа, загрузка фото брака, получение уведомлений о задержках.
4. Настроить retry/dead-letter очередь для вебхуков (устойчивость к временной недоступности внешних систем — учесть риск, отмеченный в старом ТЗ п.5.1, «единая точка отказа»).
5. E2E-тест полного цикла: сделка в Bitrix → заказ в системе → план → производство → склад → отгрузка → оплата → обратная синхронизация в 1С/Bitrix.

**Критерий готовности:** вебхуки принимаются и обрабатываются идемпотентно, есть мониторинг ошибок интеграции (аналог `LogErrors`, но с алертингом, а не молчаливым накоплением ошибок).

## Общий принцип для агента на каждом этапе

1. Прочитать соответствующий(е) `docs/*.md` файл(ы) полностью перед началом кода.
2. Не переходить к следующему этапу, пока не выполнен «Критерий готовности» текущего.
3. При расхождении между документами (например, поле упомянуто в `01` иначе, чем в `03`) — не додумывать, а зафиксировать вопрос в `docs/OPEN_QUESTIONS.md` и предложить наиболее логичный вариант, явно пометив его как допущение.
4. Каждый этап — отдельная ветка/PR с описанием, что реализовано, со ссылкой на соответствующий раздел документации.
