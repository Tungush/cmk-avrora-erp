# Готовые промпты для AI-агента разработки

Копировать по одному, отправлять агенту строго по порядку. Каждый промпт предполагает,
что папка `docs/` (с файлами 01–05) уже лежит в корне репозитория.

---

## Промпт 1 — DB / ORM

```
Прочитай docs/01_DATA_MODEL.md полностью.

Задача: реализовать слой данных (Этап 1 из docs/05_DEV_ROADMAP.md).

1. Инициализируй backend-проект (стек: [укажи свой, например Node.js + NestJS + Prisma + PostgreSQL, 
   или Python + FastAPI + SQLAlchemy + PostgreSQL] — если не уверен, предложи стек и обоснование перед тем как начать).
2. Создай схему БД / ORM-модели для всех сущностей из docs/01_DATA_MODEL.md: articles, price_history,
   materials, bom_items, customers, orders, order_lines, payment_documents, payments, acceptance_acts,
   material_stock_movements, finished_goods_movements, min_stock_levels, production_plan_items,
   production_stages, work_calendar_days, employees, users, roles, audit_log.
3. Строго соблюдай пометки Input/Calculated из документа — calculated-поля не должны быть
   заполняемыми напрямую через ORM create/update снаружи сервисного слоя.
4. Настрой FK, UNIQUE и NOT NULL констрейнты согласно разделу "Правила валидации" документа.
5. Напиши сидер, который генерирует work_calendar_days на текущий и следующий календарный год
   (выходные — суббота/воскресенье, плюс параметризуемый список праздников).
6. Напиши сидер базовых справочников: roles (10 ролей из docs/04_ROLES_PERMISSIONS.md), 
   категории материалов (Инструменты, Металл, Метизы, Комплектующие, Расходники).
7. Напиши тесты, проверяющие констрейнты (дубликат article_code -> ошибка, order_line с qty<=0 -> ошибка и т.д.).

Не переходи к бизнес-логике и API — только слой данных. По завершении покажи структуру
миграций и краткий отчёт, что реализовано и какие допущения были сделаны по стеку/деталям,
не описанным явно в документе.
```

## Промпт 2 — Бизнес-логика

```
Прочитай docs/02_BUSINESS_LOGIC.md полностью. DB/ORM уже реализован по docs/01_DATA_MODEL.md
(Этап 1 завершён).

Задача: реализовать сервисный слой бизнес-логики (Этап 2 из docs/05_DEV_ROADMAP.md).

1. Реализуй как отдельные, изолированно тестируемые сервисы/функции все формулы из раздела 2
   документа (spec_price, price_deviation_pct, lead_time_days, hour_cost, min stock/deficit,
   demand_from_orders, qty_to_produce, purchase_qty, balance_due, overdue_days).
2. Реализуй event-driven пересчёт по таблице событий из раздела 1: OrderLineCreated,
   StockMovementPosted, PriceChanged, BomChanged -> соответствующие пересчёты агрегатов.
3. Реализуй state machine статуса заказа (раздел 3): переходы, валидация условий перехода,
   запрет недопустимых переходов с понятной ошибкой.
4. Реализуй scheduled job пересчёта overdue_days (ежедневный батч) и подготовь точку
   расширения для будущих уведомлений (не реализовывать сами уведомления — это Этап 5).
5. Покрой каждую формулу unit-тестами с явными числовыми примерами (можешь использовать
   значения-заглушки, но логика должна точно соответствовать псевдокоду/SQL из документа).
6. Проверь бизнес-правила из раздела 4 документа (нельзя Shipped без полного резерва,
   soft-delete материалов при наличии ссылок в bom_items и т.д.) как guard-условия в сервисах.

Не создавай HTTP-эндпоинты — только сервисный слой и его тесты. По завершении покажи
список реализованных сервисов и результат прогона тестов.
```

## Промпт 3 — Backend API

```
Прочитай docs/03_API_SPECIFICATION.md и docs/04_ROLES_PERMISSIONS.md полностью.
DB/ORM (Этап 1) и бизнес-логика (Этап 2) уже реализованы.

Задача: реализовать REST API v1 (Этап 3 из docs/05_DEV_ROADMAP.md).

1. Реализуй все эндпоинты из docs/03_API_SPECIFICATION.md разделов 1-4 (Catalog, Orders/Planning,
   Warehouse, Finance) поверх сервисов из Этапа 2. Формат ошибок, пагинация и версионирование —
   строго по разделу 7 документа.
2. Подключи JWT-аутентификацию и RBAC guard/middleware по матрице прав из
   docs/04_ROLES_PERMISSIONS.md раздел 2 — каждый эндпоинт должен явно проверять роль/право,
   отказ -> 403 с понятным кодом ошибки.
3. Реализуй audit log middleware (docs/04_ROLES_PERMISSIONS.md раздел 4): автоматическая запись
   на каждый POST/PATCH/DELETE и на каждый переход статуса заказа, с before/after/userId.
4. Сгенерируй OpenAPI/Swagger-документацию из кода и сверь её с docs/03_API_SPECIFICATION.md —
   если есть расхождения, зафиксируй их явно в отчёте (не молчи о них).
5. Напиши интеграционные тесты на сценарий: создать заказ -> подтвердить -> провести движение
   склада -> перевести в InProduction -> ReadyToShip -> Shipped -> Closed, с проверкой RBAC
   на каждом шаге (запрет действия без нужной роли).

Эндпоинты вебхуков (/webhooks/*) и интеграции — НЕ реализовывать сейчас, это Этап 5.
Frontend — НЕ реализовывать, это Этап 4. По завершении покажи список реализованных
эндпоинтов и результаты тестов.
```

## Промпт 4 — Frontend UI

```
Backend API (Этап 3) полностью реализован и задокументирован (Swagger доступен).
Прочитай docs/04_ROLES_PERMISSIONS.md (матрица ролей) и docs/03_API_SPECIFICATION.md
(доступные эндпоинты) полностью.

Задача: реализовать frontend (Этап 4 из docs/05_DEV_ROADMAP.md).

1. Разверни каркас приложения: авторизация (JWT), роутинг с учётом роли пользователя,
   основной лейаут (сайдбар с модулями: Заказы, Производственный план, Склад, Финансы,
   Справочники, Дашборд).
2. Экран "Заказы": таблица с фильтрами (статус, заказчик, ответственный, только просроченные),
   модальная форма создания заказа пошаговым мастером (клиент -> позиции -> оплата -> план вывоза),
   действия смены статуса согласно допустимым переходам state machine.
3. Экран "Производственный план": таблица агрегатов по неделе/месяцу/кварталу с переключателем
   периода + визуализация в виде Гант-диаграммы с drag-n-drop переноса плановых сроков.
4. Канбан-доска этапов производства (ОС -> Чертежи -> Закуп -> Резка -> Сборка/сварка ->
   Покраска -> Обшивка -> Готово) с drag-n-drop карточек заказа между колонками, кнопка
   загрузки фото брака на карточке.
5. Экраны склада: приход/расход ТМЦ и ГП (быстрый inline-ввод таблицей), заявка на закупку
   с группировкой по категории материала и автосводом суммы.
6. Экраны финансов: реестр договорных обязательств, платежи, сводная дебиторская задолженность.
7. Дашборд руководителя: KPI-карточки (план/факт производства, загрузка цеха в чел/часах,
   дебиторка, остатки ГП против норматива).
8. Обязательно: визуально и функционально разделяй Input-поля (редактируемые) и Calculated-поля
   (только чтение, другой стиль) на всех формах — сверяйся с пометками в docs/01_DATA_MODEL.md.
9. UI должен скрывать/дизейблить действия, недоступные текущей роли пользователя согласно
   матрице из docs/04_ROLES_PERMISSIONS.md, но помни, что финальная проверка прав — на бэкенде,
   фронт не единственный барьер.

По завершении покажи карту экранов/роутов и список того, что осталось как заглушка (если есть).
```

## Промпт 5 — Интеграции

```
Backend API (Этап 3) и Frontend (Этап 4) реализованы. Прочитай docs/03_API_SPECIFICATION.md
раздел 5 (вебхуки) и docs/05_DEV_ROADMAP.md раздел "Этап 5" полностью.

Задача: реализовать интеграционный слой (Этап 5 из docs/05_DEV_ROADMAP.md).

1. Реализуй приём вебхуков:
   - POST /webhooks/bitrix/deal-updated (проверка X-Bitrix-Signature, upsert orders.bitrixDealId/bitrixStage)
   - POST /webhooks/1c/payment-posted (создание Payment по doNumber)
   - POST /webhooks/1c/stock-updated (создание MaterialStockMovement по materialCode)
   - POST /webhooks/telegram/stage-confirmed (обновление production_stages)
   Все — с проверкой подписи/авторизации и идемпотентностью по внешнему ID (повторная доставка
   одного и того же события не должна создавать дубли).
2. Реализуй исходящие интеграции: при смене статуса заказа на ReadyToShip/Shipped — отправка
   события в Bitrix24 (статус готовности, дата отгрузки); при создании finished_goods_movement
   типа "приход с производства" — отправка события в 1С (факт выпуска, списание сырья по BOM).
3. Реализуй Telegram-бота для мастера цеха: команда подтверждения этапа по заказу, приём фото
   брака, отправка уведомлений о просроченных заказах (используя job из Этапа 2, п.4).
4. Настрой retry с экспоненциальной задержкой и dead-letter очередь для исходящих интеграций —
   учти риск "единой точки отказа", отмеченный в анализе исходного Excel-файла.
5. Добавь мониторинг/алертинг ошибок интеграции (лог ошибок с уведомлением ответственного,
   а не молчаливое накопление, как было в листе LogErrors исходного файла).
6. Напиши E2E-тест полного цикла: имитация вебхука сделки из Bitrix -> создание заказа ->
   попадание в план -> движение склада -> отгрузка -> оплата -> проверка исходящего события
   в 1С/Bitrix (можно мокать внешние API).

По завершении покажи список реализованных интеграционных точек, схему retry/dead-letter
и результаты E2E-теста.
```
