# ЦМК АВРОРА — этапы производства, себестоимость заказа и партионный учёт

Документ отвечает на вопрос: **почему тот же самый заказ через месяц стоит других денег — и как увидеть причину, а не гадать.**

Опирается на: [07_ARCHITECTURE_AND_UX.md](07_ARCHITECTURE_AND_UX.md) (§3, модуль трудочасов), [06_SHEET_ANALYSIS_AND_DESIGN.md](06_SHEET_ANALYSIS_AND_DESIGN.md) (§3.3, формулы), [08_INTEGRATION_1C.md](08_INTEGRATION_1C.md) (владение данными).

Решения приняты в обсуждении 19.08.2026. Пункты, отданные на усмотрение разработки с формулировкой «максимально гибко и точно», отмечены как **решение по данным** — с указанием, какая цифра из базы его продиктовала.

---

## 0. Отправная точка: четыре разрыва

**1. Этапы производства перемешаны с продажей.** В `StageCode` восемь значений одним списком: ОС с заказчиком, Общий вид, Чертежи, Закуп, Резка, Сборка/сварка, Покраска, Обшивка. Первые два — стадия сделки, а не цеха. Последние четыре — переделы, и они дублируют `RoutingStage`, по которому считается себестоимость. Два независимых списка про одно и то же не сойдутся никогда.

**2. Цена материала — одно поле.** `Material.purchasePrice` хранит «как сейчас». История приходов есть — 523 прихода на 307 материалов за год, — но расчёт её не видит.

**3. Снимок себестоимости хранит только итоги.** `ArticleCosting` знает, что материалы стоили 412 000 ₸, но не знает, из каких цен это сложилось. На вопрос «почему подорожало» ответить нечем.

**4. Подряда в модели нет.** Есть `WorkCenter` со ставкой — и всё. Работу, отданную на сторону, вписать некуда.

Цена вопроса измерима. Разброс закупочных цен по одному материалу за год:

| Материал | Партий | Цена мин → макс | Разброс |
|---|---|---|---|
| Лист г/к 1500×6000×20мм | 7 | 345 000 → 471 000 ₸/т | +37 % |
| Труба проф. 180×180×5мм | 3 | 431 000 → 544 000 ₸/т | +26 % |
| Труба проф. 80×80×5мм | 4 | 440 000 → 551 000 ₸/т | +25 % |

Тот же заказ, посчитанный по разным партиям, отличается на треть. Сейчас выбор партии не существует как понятие — берётся то, что лежит в справочнике на момент нажатия кнопки.

## 1. Главный принцип

> **Справочник хранит «как сейчас». Документ хранит «как было».**

Всё, что влияет на деньги, замораживается в документ вместе со своими ценами, нормами, коэффициентами и **ссылками на источники**. После этого справочник может меняться сколько угодно — согласованные заказы не поедут.

Это тот же приём, что в [08_INTEGRATION_1C.md §1](08_INTEGRATION_1C.md): там разграничили владение между системами, здесь — между «сейчас» и «тогда». Без ссылок на источники принцип не работает: снимок, хранящий только числа, отвечает «стало дороже», а нужен ответ «партия от 15.04 по 345 000 закончилась, доступна только от 12.07 по 471 000».

## 2. Этапы: два уровня вместо восьми в ряд

### 2.1. Новая структура

```prisma
enum OrderStageCode {
  DESIGN      @map("КД")            // бывшие «Чертежи»
  SUPPLY      @map("Снабжение")     // бывший «Закуп»
  PRODUCTION  @map("Производство")  // цех, три передела
}
```

Внутри `PRODUCTION` — **существующий** `RoutingStage`, без изменений:

```
CUTTING   Резка
ASSEMBLY  Сборка / сварка / обшивка
PAINTING  Зачистка / покраска
```

Ключевой выигрыш: один справочник переделов и для нормирования себестоимости, и для отслеживания цеха. Мастер закрывает «Сборку» — фактические часы ложатся в план/факт себестоимости без второго ввода.

«ОС с заказчиком» и «Общий вид» убираются из этапов производства: это стадия продажи, её место в `Order.status` и `bitrixStage`.

### 2.2. Гранулярность отметки — адаптивная

**Решение по данным.** Распределение заказов по числу позиций:

| Позиций | Заказов | Доля |
|---|---|---|
| 1 | 870 | 39,5 % |
| 2–3 | 238 | 10,8 % |
| 4–10 | 473 | 21,5 % |
| 11–30 | 572 | 26,0 % |
| 31+ | 49 | 2,2 % |

Половина заказов — до трёх позиций, там одна галочка на заказ идеальна. Но 28 % содержат 11 и больше, и для них «резка по заказу целиком» бессмысленна: половина деталей нарезана, половина нет, а галочка одна. Поэтому режим не фиксируется, а выбирается:

```prisma
enum StageTrackingMode { ORDER, LINE }

model Order {
  stageTrackingMode StageTrackingMode @default(ORDER) @map("stage_tracking_mode")
}
```

Правило подстановки: позиций ≤ порога (настройка в `CostingConfig`, по умолчанию **5**) → `ORDER`; больше → `LINE`. Переопределяется вручную на конкретном заказе в обе стороны.

В режиме `LINE` мастер получает кнопку «отметить все» — то есть в худшем случае это та же одна галочка, но с возможностью раскрыть и отметить точечно. Простота не теряется, точность появляется там, где нужна.

Модель одна и та же:

```prisma
model ProductionStage {
  orderId      String
  orderLineId  String?         // NULL в режиме ORDER
  stageCode    OrderStageCode
  routingStage RoutingStage?   // заполнен только для PRODUCTION
  status       StageStatus
  actualWorkers Decimal?
  actualHours   Decimal?
  completedAt, completedById, defectPhotoUrl

  @@unique([orderId, orderLineId, stageCode, routingStage])
}
```

### 2.3. Раскладка факта по позициям

В режиме `ORDER` мастер вводит один факт на передел, а система раскладывает его по позициям **пропорционально нормативной трудоёмкости**:

```
Факт по сборке: 120 ч на заказ
Нормы:  Ферма Ф-200 ×4  →  80 % трудоёмкости сборки  →  96 ч
        Балка Б-15  ×2  →  20 %                       →  24 ч
```

Раскладка вычисляемая, не хранимая: при правке нормы или факта она пересчитывается сама. В режиме `LINE` раскладка не нужна — факт уже введён по позициям.

### 2.4. Миграция существующих данных

```
OS_WITH_CUSTOMER  →  удаляется из этапов, признак переносится в Order.status
GENERAL_VIEW      →  то же
DRAWINGS          →  DESIGN
PROCUREMENT       →  SUPPLY
CUTTING           →  PRODUCTION + routingStage = CUTTING
WELDING_ASSEMBLY  →  PRODUCTION + routingStage = ASSEMBLY
CLADDING          →  PRODUCTION + routingStage = ASSEMBLY   ← как в «Спецификациях 2022»
PAINTING          →  PRODUCTION + routingStage = PAINTING
```

Исходный код кладётся в `legacyStageCode` и никогда не удаляется — отчёты за прошлые периоды должны воспроизводиться. `Обшивка` вливается в `ASSEMBLY` ровно так же, как это было сделано в исходной таблице при расчёте трудочасов.

## 3. Себестоимость: калькуляция заказа как документ

`ArticleCosting` остаётся снимком по изделию — «сколько стоит Ферма Ф-200 вообще». Поверх него появляется калькуляция **заказа** — «сколько стоит эта ферма в этом заказе, посчитанная тогда-то и по таким-то партиям».

### 3.1. Модель

```prisma
model OrderCosting {
  id, orderId, orderLineId, articleId, qty
  version          Int
  status           CostingStatus     // DRAFT | APPROVED | ARCHIVED
  calculatedAt, approvedAt, approvedById
  baseCostingId    String?           // с какой версией сравниваем

  // замороженные коэффициенты
  hourlyRate       Decimal
  logisticsPct     Decimal
  logisticsMode    LogisticsMode     // PERCENT_OF_MATERIAL | FIXED_AMOUNT | PER_KG
  logisticsFixed   Decimal?
  utilitiesPct     Decimal
  marginPct        Decimal
  marginMode       MarginMode        // MARGIN | MARKUP
  vatPct           Decimal
  ratesSource      String            // 'config' | 'manual'
  ratesReason      String?           // обязателен при manual

  // итоги
  materialCost, laborCost, contractorCost, logisticsCost, utilitiesCost
  totalCost, margin, price
}

model OrderCostingMaterial {
  costingId, materialId
  materialCodeSnapshot, materialNameSnapshot   // имя на момент расчёта
  qtyPerUnit, qtyTotal
  unitPrice
  priceSource      PriceSource
  batchId          String?    // конкретная партия
  sourceDocumentId String?    // приход / ДО
  priceDate        DateTime
  isShortage       Boolean    // посчитано по прогнозной цене, партии нет
  lineCost
}

model OrderCostingLabor {
  costingId, stage
  laborKind        LaborKind  // STAFF | CONTRACTOR
  workCenterId, contractorId
  share, rateType, rate, countInShopHours
  workers, hoursPerUnit, hourlyRate
  lineCost
}
```

Имена материалов сохраняются копией: если через полгода номенклатуру в 1С переименуют, старая калькуляция должна читаться в тех словах, в которых её согласовывали.

### 3.2. Коэффициенты: каскад и режимы

Каскад переопределения, побеждает нижний уровень:

```
CostingConfig  (глобально, версионно)
   └── Article  (по изделию, опционально)
         └── OrderCosting  (по калькуляции — последнее слово)
```

**Логистика.** 3 % — только значение по умолчанию. Режимы:

| Режим | Формула | Когда |
|---|---|---|
| `PERCENT_OF_MATERIAL` | материалы × 3 % | по умолчанию |
| `FIXED_AMOUNT` | сумма как есть | одна фура на заказ |
| `PER_KG` | тариф × `Article.weightKg` × кол-во | тяжёлые дешёвые изделия |

**Маржа.** Маржинальность **35 % от цены**, а не наценка:

```ts
// MARGIN (по умолчанию, 35 %)
price  = totalCost / (1 - marginPct);   margin = price - totalCost;

// MARKUP (прежнее поведение, оставлено для совместимости)
margin = totalCost * marginPct;         price  = totalCost + margin;
```

Проверка на себестоимости 1 000 000 ₸: цена 1 538 462, маржа 538 462, доля маржи в цене 35,0 %. Наценка при этом 53,8 %.

Обязательные требования к реализации:

- `marginPct < 1` — валидация на входе, иначе деление на ноль;
- в интерфейсе **обе цифры рядом**: «маржа 35 % от цены = наценка 53,8 %». Иначе менеджер, привыкший к прежним 10 %, решит, что цена выросла в пять раз;
- НДС 12 % накручивается сверху цены и в маржу не входит;
- старые калькуляции не пересчитываются: у них в снимке свой режим и свой процент;
- любое ручное значение логистики или маржи требует причину, пишется в аудит и **видно в разборе формулы**: «логистика 5 % — вручную, Петров, „доставка в Актау"». Иначе через месяц никто не вспомнит, почему тут пятёрка.

### 3.3. Три слоя себестоимости заказа

| Слой | Источник | Отвечает на вопрос |
|---|---|---|
| **План** | заморожен при согласовании цены | во что оценили |
| **Факт закупа** | ДО и приходы, привязанные к заказу | почём реально купили |
| **Факт производства** | часы из цеха | сколько реально сделали |

Цепочка «заказ клиента → GET D → GET C → приход» уже работает ([08_INTEGRATION_1C.md §4.3](08_INTEGRATION_1C.md)), так что второй слой собирается из готовых данных. Отсюда бесплатно получается экран «Рентабельность заказа: план vs факт» — то, чего в таблице не было в принципе.

## 4. Партии и выбор закупочной цены

### 4.1. Модель

```prisma
model MaterialBatch {
  id, materialId
  receiptDate, unitPrice
  qtyReceived, qtyRemaining        // остаток живой
  supplierId, supplierName
  sourceDocumentId                 // ДО / накладная
  origin        BatchOrigin        // LOCAL | ONEC
  externalId    String?            // документ или серия 1С
  priceAnomaly  Boolean @default(false)
  createdAt
}
```

Партия создаётся приходом. Точка уже существует — [material-receipt.service.ts](backend/src/services/material-receipt.service.ts), там же где сейчас пересчитывается средневзвешенная цена.

Объём подтверждает реализуемость: 523 прихода на 307 материалов за год, у большинства материалов **1–3 партии**, больше десяти — только у трёх. В интерфейсе будет не портянка, а две-три строки на выбор.

### 4.2. Что видит человек

```
Лист г/к 1500×6000×20мм — требуется 1 240 кг

  ○ Партия 12.07.2026   471 000 ₸/т    остаток   800 кг   ДО-1204 · Металлсервис
  ○ Партия 03.06.2026   408 000 ₸/т    остаток   500 кг   ДО-1101 · КазМеталл
  ○ Партия 15.04.2026   345 000 ₸/т    остаток    90 кг   ДО-0987 · Металлсервис
                                       ─────────────────
                                       доступно 1 390 кг ✓

  Режим: ● По остаткам, старые первыми   ○ Конкретная партия
         ○ Средневзвешенная по остаткам  ○ Последняя закупочная
         ○ Прайс поставщика              ○ Вручную

  → 90×345 + 500×408 + 650×471 = 541 200 ₸   (средняя 436 452 ₸/т)
```

```prisma
enum PriceSource {
  FIFO_STOCK      // по остаткам, старые первыми — по умолчанию
  SPECIFIC_BATCH
  WEIGHTED_AVG
  LAST_PURCHASE
  PRICE_LIST
  MANUAL          // требует причину
}
```

### 4.3. Дефицит остатков

Требуется 1 240 кг, в партиях 900. Дефицит считается по цене последнего прихода (или по ожидаемой цене закупа, если снабжение её проставило) и **явно помечается** — `isShortage = true`, в расчёте отдельной строкой:

```
340 кг посчитаны по прогнозной цене 471 000 ₸/т — партии нет
```

Без этой пометки менеджер продаст по цене, которой не существует.

### 4.4. Резерв партии и перехват

```prisma
model BatchReservation {
  batchId, orderId, orderCostingId, qty
  status      ReservationStatus  // ACTIVE | RELEASED | OVERRIDDEN | EXPIRED
  expiresAt
  createdById, releasedById, releaseReason
}

model BatchOverrideRequest {
  reservationId, requestedByOrderId, qtyRequested, reason
  status      OverrideStatus     // PENDING | APPROVED | REJECTED
  requestedById, decidedById, decidedAt, decisionComment
}
```

Порядок:

1. Калькуляция уходит в `APPROVED` → под выбранные партии создаются резервы.
2. Второй менеджер выбирает ту же партию и видит прямо в строке:
   > ⚠ Партия 15.04 · 345 000 ₸/т — **800 кг зарезервировано** под П-88192-21 (Иванов, до 25.08). Свободно 90 кг.
3. Он может взять свободный остаток и добрать из другой партии — **без согласования**, система сама покажет новую цену. Либо нажать «Запросить партию» с указанием причины и объёма.
4. **Согласует директор.** На одном экране: чей резерв, оба заказа с датами отгрузки, на сколько подорожает заказ, у которого забирают, есть ли возможность докупить. Решение в один клик с комментарием.
5. При одобрении калькуляция первого заказа помечается «требует пересчёта», менеджеру падает задача, и если отклонение больше порога — поднимается `PriceReviewRequest`. Автоматически цену не меняем: она могла уже уйти клиенту. Механизм готов — [article-costing.service.ts:118](backend/src/services/article-costing.service.ts:118).

Чтобы решение не встало колом на одном человеке:

- уведомление в Telegram — поле `Employee.telegramId` уже есть;
- менеджер не заблокирован: пока запрос висит, он считает по доступным партиям и работает дальше;
- запросы старше суток подсвечиваются в списке — не эскалация, а видимость: если очередь начнёт копиться, это будет заметно за неделю, а не через квартал.

**Срок жизни резерва.** Заказ не ушёл в `IN_PRODUCTION` за 30 дней → за 3 дня уведомление менеджеру → резерв снимается автоматически, событие пишется в аудит. Срок и предупреждение — настройки в `CostingConfig`. Без этого через полгода весь металл окажется «занят» мёртвыми коммерческими предложениями.

**Резерв учётный, а не физический.** Кладовщик выдаёт металл по факту, а не по резервам. Расхождение «зарезервировано под А, ушло в Б» попадает в отчёт сверки, а не ломает молча себестоимость обоих заказов.

### 4.5. Карантин аномальных цен вместо глобальной чистки

**Решение по данным.** Из 91 материала с несколькими приходами аномалия обнаружена у **двух**, сильный разброс — у одного:

| Класс | Материалов |
|---|---|
| норма (<1,5×) | 88 |
| сильный разброс (1,5–5×) | 1 |
| аномалия (>5×) | 2 |

Пример аномалии: «Труба э/с ф76×3,5» с приходами по 2 548 и по 430 000 — это цена за метр против цены за тонну в одном материале.

Три материала не оправдывают чистку всего справочника как предусловие запуска. Поэтому — карантин:

- при создании партии цена сверяется с медианой по материалу; отклонение больше порога (по умолчанию **5×**, настройка) → `priceAnomaly = true`;
- такая партия **не участвует** в автоматическом FIFO и не подставляется в расчёт молча;
- в выборе она видна с предупреждением и требует явного подтверждения снабжения;
- отдельный экран «Материалы с подозрительными ценами» — сейчас там будет три строки, разбираются за час.

Схема самоочищающаяся: новые ошибки ввода единиц измерения ловятся тем же детектором, а не всплывают через год в себестоимости.

### 4.6. Отношения с 1С

**Решение по данным.** В текущем контракте GET-запросов ([08_INTEGRATION_1C.md §5](08_INTEGRATION_1C.md)) партий и серий нет: есть заказ поставщику (GET C) и поступление товаров. Значит партия у нас = приход, и это работает уже сейчас.

Чтобы вопрос «ведёт ли 1С партионный учёт» перестал быть блокирующим, модель спроектирована под оба сценария:

| `origin` | Источник | Поведение |
|---|---|---|
| `LOCAL` | наш приход | партия редактируется у нас |
| `ONEC` | партия/серия 1С | поля только для чтения, расхождения идут в отчёт сверки |

Если 1С позже начнёт отдавать партии — включается режим `ONEC`, меняется только маппинг. Переписывать расчёт не придётся.

## 5. Трудозатраты: штат и подряд

### 5.1. Модель

```prisma
model Contractor {
  id, name, binIin
  defaultRateType     RateType
  defaultRate         Decimal
  defaultWorkLocation WorkLocation   // OUR_SHOP | CONTRACTOR_SITE
  isActive, notes
}

model OrderLaborAssignment {
  orderId, orderLineId, articleId, stage
  laborKind        LaborKind     // STAFF | CONTRACTOR
  workCenterId, contractorId
  share            Decimal       // доля объёма, 0…1
  rateType         RateType
  rate             Decimal
  countInShopHours Boolean
  plannedHours, actualHours
  contractDocId, note
}
```

Норма — свойство изделия, исполнитель — свойство заказа. Подряд это ситуативное решение («не успеваем — обшивку отдали на сторону»), и влияет оно на себестоимость конкретного заказа, а не на эталон в справочнике. При создании калькуляции нормы копируются из артикула в `OrderCostingLabor` и дальше живут своей жизнью.

### 5.2. Типы ставок и защита от молчаливых нулей

| Тип | Ввод | Расчёт |
|---|---|---|
| `PER_HOUR` | ₸ / час | чел × ч × кол-во × доля × ставка |
| `PER_UNIT` | ₸ / шт | кол-во × доля × ставка |
| `PER_KG` | ₸ / кг | кол-во × доля × `weightKg` × ставка |
| `PER_TON` | ₸ / т | кол-во × доля × `weightKg` / 1000 × ставка |
| `FIXED` | ₸ за объём | ставка как есть |

**Решение по данным.** Вес заполнен у **70 артикулов из 2 161** (3,2 %), а у материалов — у **0 из 3 147**. Значит весовые ставки на 97 % изделий молча дали бы ноль. Поэтому:

- системный дефолт — **`PER_UNIT`**: количество известно точно всегда, вес — почти никогда;
- `PER_KG` и `PER_TON` видны в списке, но **заблокированы**, если `weightKg = 0`, с подсказкой «у изделия не заполнен вес»;
- сохранение весовой ставки при нулевом весе запрещено — никаких нулей по умолчанию;
- `Contractor.defaultRateType` перекрывает системный дефолт и запоминается по последнему использованию: дефолт обучается на практике вместо того, чтобы угадываться заранее.

### 5.3. Где выполняются работы

Флаг `countInShopHours` формулируется по-человечески:

> **Где выполняются работы?**
> ● В нашем цеху → часы идут в трудозатраты цеха, участок считается занятым
> ○ На площадке подрядчика → отдельная строка «Услуги подрядчиков», мощность цеха свободна

Различие содержательное: подряд, работающий бок о бок со штатом, реально занимает участок и должен быть виден в загрузке; подряд, которому увезли обшивку на сторону, вашу мощность не трогает. Значение подставляется из `Contractor.defaultWorkLocation`, но переопределяется в каждом заказе — один и тот же подрядчик в июле работал у вас, а в августе у себя.

**Обязательная проверка:** если ставка сдельная, а работы идут в нашем цеху, часов в расчёте нет вообще — планирование мощности получит ноль и покажет свободный цех, которого нет. В этом случае форма требует оценку часов в `plannedHours`.

### 5.4. Смешанный случай

Один передел, один заказ, две строки:

```
Сборка / сварка / обшивка, Ферма Ф-200 ×4
  ├ Штат · участок СБ-1 · доля 50 %   →  1 чел × 0,15 ч × 4 × 0,5 × 2 040 ₸ =    612 ₸
  └ Подряд · ТОО «Мехмонтаж» · 50 % · 18 000 ₸/шт · в нашем цеху
                                      →  4 × 0,5 × 18 000 ₸                 = 36 000 ₸
                                                                              ─────────
                                                                  Итого передел  36 612 ₸
```

Валидация: сумма долей по (заказ, позиция, передел) = 1. Одна строка → доля 1 по умолчанию; в обычном случае проценты вводить не нужно.

В отчётах два числа рядом:

```
Трудозатраты цеха:        96 ч   (штат 60 ч + подряд у нас 36 ч)
Услуги подрядчиков:  128 000 ₸   (из них на стороне 92 000 ₸)
```

## 6. Сравнение версий: почему через месяц дороже

`GET /orders/:id/costing/compare?base=v1&target=v3` раскладывает дельту на факторы. По каждому материалу:

```
q₂p₂ − q₁p₁  =  q₁(p₂−p₁)   +   p₂(q₂−q₁)
                эффект цены      эффект нормы
```

Новые и удалённые позиции относятся целиком на «изменение состава». Аналогично по труду: отдельно эффект ставки, отдельно эффект нормы, отдельно смена исполнителя со штата на подряд.

Что видит человек:

```
Заказ П-88192-21, версия 19.08.2026 vs 15.07.2026:  +412 300 ₸ (+18,4 %)

  Материалы                    +350 000
    ├ рост закупочных цен      +310 000   лист г/к 20мм: партия 15.04 по 345 000 ₸/т
    │                                     исчерпана, доступна 12.07 по 471 000 ₸/т
    │                                     (ДО-1204, Металлсервис) → +126 000 ₸/т
    └ изменение состава         +40 000   добавлены 4 петли — инженер Иванов, 03.08
  Труд                          +30 000
    ├ ставка                    +20 000   2 040 → 2 200 ₸/час с 01.08
    └ нормы                     +10 000   сборка 0,15 → 0,18 ч
  Логистика                      +8 000   3 % → 3,5 % (вручную, Петров: «доставка в Актау»)
  Маржа                         +24 300   35 % без изменений, эффект базы
```

Это и есть ответ на исходный вопрос: не «стало дороже», а «вот из-за чего, вот когда и вот кто это сделал».

## 7. Номенклатура: контроль имён, который не опирается на память

### 7.1. Проблема уже случилась

Замер по текущему справочнику:

| Показатель | Значение |
|---|---|
| Групп дублирующихся наименований материалов | **82** |
| Материалов в них | 168 из 3 147 (5,3 %) |
| Групп дублей среди артикулов | 30 |
| Заявок на номенклатуру в базе | **2** |

Буквальные дубли: «Круг ф 12 мм» ×2, «Труба профильная 200×200×5 мм» ×2, «Уголок 90×90×6 мм» ×2 — разные записи одного и того же. Плюс варианты, различающиеся только пробелами: «Круг ф 6,5 мм» и «Круг ф6,5мм», «Швеллер 12У» и «Швеллер 12 У».

Наивный SQL-ключ (убрать всё, кроме букв и цифр) находил 79 групп: он не видел вариантов с пробелами и при этом ложно склеивал «5х2,5» с «5х25». Нормализация из §7.6 находит 82 группы и ложный дубль не создаёт.

Две заявки на 3 147 материалов означают, что процесс заведения через заявку фактически не используется: номенклатуру создают мимо него. Значит вопрос «как контролировать через N месяцев» не гипотетический — это уже произошло 79 раз.

### 7.2. Принцип

Сценарий: завели заявку «Уголок 50х50 ст3», 1С присвоила «Уголок равнополочный 50×50×5 ГОСТ 8509-93», код `00-00012345`. Через два месяца сотрудник ищет — и не находит.

Уведомление в момент присвоения тут не спасает:

> **Уведомление решает первые сутки. Через два месяца работает только то, для чего память не нужна.**

Хуже того, на память полагаться нельзя даже теоретически: имя в 1С может **измениться после** заведения, и тогда устареет даже правильно запомненное. А если сотрудник уволился, его память не поможет никому.

Поэтому контроль строится не на том, чтобы человек запомнил имя 1С, а на том, чтобы имя 1С было **не нужно знать**. Три контура.

### 7.3. Контур 1 — не дать создать дубль

Перед созданием заявки — обязательный поиск похожего. Кандидаты показываются с именем 1С, кодом, единицей измерения и последней ценой закупа:

```
Вы вводите: «уголок 50х50 ст3»

  Похоже, это уже есть:
  ▸ Уголок равнополочный 50×50×5 ГОСТ 8509-93
    код 1С 00-00012345 · кг · последний закуп 12.07 по 471 000 ₸/т
    ↳ заведён по заявке №142 от 12.06, автор Иванов
       изначально просили: «Уголок 50х50 ст3»

  [ Да, это оно ]   [ Нет, другое — продолжить заявку ]
```

Нажал «Да, это оно» → его формулировка **добавляется алиасом**, и в следующий раз он найдёт материал своими словами сразу. Нажал «Нет» → указывает, чем отличается; это попадает в заявку и помогает тому, кто будет заводить в 1С.

### 7.4. Контур 2 — найти, не зная имени 1С

Это прямой ответ на вопрос «а если сотрудник забудет».

**Слова заявки живут вечно.** Исходная формулировка автора сохраняется навсегда как алиас и работает как поисковый ключ. Помнить имя 1С не надо — надо помнить свои собственные слова, а свои слова человек помнит.

**Справочник обучается на неудачных поисках.** Каждый запрос, не давший результата, логируется. Если человек искал «уголок равнополочный 50», ничего не нашёл, а через минуту открыл нужный материал или подтвердил его в контуре 1 — связка «запрос → материал» становится новым алиасом. Через год материал находится по десятку формулировок, которыми его называют реальные люди, а не по одной канонической из 1С.

**Личный след.** Экран «Моя номенклатура»: всё, что сотрудник когда-либо заводил или подтверждал, с итоговым именем и кодом 1С. Помнить имя не нужно — достаточно помнить «я это заводил», что несравнимо легче.

**Поиск от контекста, а не от имени.** Материал находится оттуда, где он уже применяется: «этот уголок стоит в 47 изделиях», «в заказе П-88192-21 брали вот это». Инженер, добавляющий позицию в состав фермы, первым делом видит то, что используется в похожих изделиях.

**Поиск по характеристикам.** Тип + размер + марка стали + ГОСТ как отдельные поля, а не как строка. «Уголок, 50×50, Ст3» находится, даже если в 1С он назван словами, которых сотрудник никогда не видел.

### 7.5. Контур 3 — поймать то, что всё-таки проскочило

**Отчёт «возможные дубли»** — регулярный, а не только в момент ввода. На сегодняшних данных он покажет 79 групп. Слияние дублей переносит состав изделий, историю приходов и алиасы на оставшуюся запись.

**Сверка справочника с 1С.** Переименовали в 1С → новое имя становится основным, **старое уходит в алиасы с датами**: «так называлось с 12.06 по 03.09». Ни поиск, ни старые калькуляции от переименования не ломаются.

**SLA на заявку.** Статусы `PENDING → APPROVED → WAITING_1C → SYNCED`. Заявка, висящая в `WAITING_1C` дольше N дней (настройка), подсвечивается и эскалируется. Без этого она тихо теряется, а сотрудник через месяц заводит новую — ровно так и получаются 79 групп дублей.

**Уведомление автору в момент присвоения** — в Telegram, поле `Employee.telegramId` уже есть. Не решает проблему N месяцев, но закрывает первые сутки и стоит дёшево.

### 7.6. Ловушка нормализации

«Кабель ВВГнг-LS 5х2,5» и «Кабель ВВГнг-LS 5х25» — **разные кабели**. Наивная нормализация (убрать всё, кроме букв и цифр) склеивает их в один дубль: запятая исчезает, `5х2,5` превращается в `5х25`. Этот ложный дубль реально присутствует в замере выше.

Правило: числа нормализуются отдельно от текста.

- разделитель дробной части сохраняется: `2,5` → `2.5`;
- размерности приводятся к одному виду: `х`, `x`, `*`, `×` → `×`;
- склейка цифр через утраченный разделитель запрещена;
- кириллическая `х` и латинская `x` считаются одним символом, как и прочие визуальные близнецы (`с/c`, `о/o`, `а/a`).

Без этого правила отчёт о дублях будет предлагать сливать разные материалы — а слияние переносит составы изделий и потому необратимо на практике.

### 7.7. Модель

```prisma
model MaterialAlias {
  id, materialId
  alias        String        // как назвали
  normalized   String        // нормализация по §7.6, индекс
  source       AliasSource   // REQUEST | ONEC | EXCEL | SUPPLIER | SEARCH_MISS | MANUAL
  validFrom, validTo         // для имён, устаревших после переименования в 1С
  createdById, createdAt

  @@index([normalized])
}

model NomenclatureRequest {
  // существующие поля +
  onecCode, onecName, onecGuid, onecUnit
  linkedMaterialId, syncedAt
  status        // PENDING | APPROVED | WAITING_1C | SYNCED | REJECTED
  slaDueAt
}

model SearchMiss {
  id, query, normalized, userId, createdAt
  resolvedMaterialId String?   // чем в итоге закончилось → кандидат в алиасы
}
```

### 7.8. Как это выглядит в интерфейсе

Везде, где материал показывается — в составе изделия, в закупе, в калькуляции, — он подписан **двумя именами**:

```
Уголок равнополочный 50×50×5 ГОСТ 8509-93        ← имя в 1С, код 00-00012345
у нас также: «Уголок 50х50 ст3», «уголок 50 равнополочный»   ← алиасы, по ним ищется
```

В карточке — полная история: кто просил, какими словами, кто завёл в 1С, когда, каким именем, как имя менялось потом. Через два месяца сотрудник открывает свою же заявку и видит, во что она превратилась.

## 9. Порядок внедрения

Все восемь шагов реализованы в коде и покрыты тестами. Миграции написаны, но **к базе не применены** — это отдельное действие.

| Шаг | Содержание | Статус | Ломает существующее? |
|---|---|---|---|
| 1 | `OrderStageCode`, миграция 8 → 3 этапа, `legacyStageCode`, `stageTrackingMode` | готово | Меняет экран «Производство»; данные сохраняются полностью |
| 2 | `marginMode` + режимы логистики в `CostingConfig`, маржа 35 % от цены | готово | Меняет **все новые** расчёты; старые снимки не трогаются |
| 3 | `MaterialBatch` из истории приходов, детектор аномалий, карантин | готово | Нет: справочные цены продолжают работать как фолбэк |
| 6 | `Contractor`, `OrderLaborAssignment`, пять типов ставок | готово | Нет |
| 4 | `OrderCosting` + строки материалов и труда, выбор партии | готово | Нет: `ArticleCosting` остаётся как есть |
| 7 | Сравнение версий и факторный анализ | готово | Нет |
| 5 | Резервы, запрос на перехват, согласование директора, авто-снятие через 30 дней | готово | Нет |
| 8 | Номенклатура: три контура — поиск-перед-заявкой, алиасы с обучением на промахах, отчёт дублей и сверка имён с 1С | готово | Нет |
| 9 | Разбор 82 существующих групп дублей через отчёт и слияние | ручная работа | Нет: слияние переносит составы и историю |

Шаг 6 пришлось поставить перед шагом 4: снимок калькуляции обязан замораживать исполнителя, иначе через месяц не видно, что половину сборки отдали на сторону.

Шаги 1 и 2 — единственные, где нужен согласованный момент переключения. Начиная с третьего всё добавляется поверх, не ломая работающее.

## Приложение: решения одной таблицей

| | Решение |
|---|---|
| Этапы | КД → Снабжение → Производство; ОС и Общий вид убраны; в цеху 3 передела из `RoutingStage` |
| Отметка цеха | Адаптивно: ≤ 5 позиций — на заказе, больше — построчно; факт раскладывается по нормам |

| Цена материала | Выбор партии пользователем, FIFO по остаткам по умолчанию; в снимке — ссылка на партию и приход |
