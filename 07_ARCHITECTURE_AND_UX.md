# ЦМК АВРОРА — архитектурный план и дизайн-концепция

Документ описывает переход от Google-таблицы к веб-сервису: ролевую модель с правами на уровне полей, UX-замену горизонтальных таблиц, модуль трудочасов и дизайн-систему.

Опирается на: [01_DATA_MODEL.md](01_DATA_MODEL.md), [04_ROLES_PERMISSIONS.md](04_ROLES_PERMISSIONS.md), [TZ_Cascade_RBAC.md](TZ_Cascade_RBAC.md), [06_SHEET_ANALYSIS_AND_DESIGN.md](06_SHEET_ANALYSIS_AND_DESIGN.md).

## 0. Что уже есть в коде и чего не хватает

Прежде чем проектировать — честная отправная точка.

| Компонент | Состояние | Пробел |
|---|---|---|
| `RbacGuard` ([rbac.guard.ts](backend/src/common/guards/rbac.guard.ts)) | Работает: `@Roles(...)` + JWT | Проверка **на уровне эндпоинта**, «пустил / не пустил». Разграничения по полям нет |
| `assertNoCalculatedFieldUpdate` ([calculated-fields.ts](backend/src/common/calculated-fields.ts)) | Работает | Хорошая основа: расчётные поля нельзя перезаписать. Осталось применить ко всем модулям |
| `pickEditableFields` | Есть | Применяется только на запись; на **чтение** проекции полей нет — себестоимость уедет в ответ API любому, кто имеет доступ к эндпоинту |
| `MODULE_ACCESS` ([roles.ts](frontend/src/utils/roles.ts)) | **Декоративный** | Все 10 ролей имеют доступ ко всем модулям, кроме `audit`. Фактически RBAC на фронте нет |
| `Role` / `UserRole` (Prisma) | Есть | Нет `Permission` — права зашиты в код декораторами, админ не может их менять |
| Матрица прав ([04_ROLES_PERMISSIONS.md](04_ROLES_PERMISSIONS.md)) | Спроектирована | Уровень сущностей, не полей. Требование «инженер вносит трудочасы, менеджер — коммерцию» ею не покрывается |

**Вывод:** нужен не новый RBAC с нуля, а достройка существующего до уровня полей и перевод прав из кода в данные.

## 1. Ролевая модель

### 1.1. Развилка: 4 роли или 10?

В задании предложены 4 роли (Администратор, Менеджер проектов, Инженер, Наблюдатель). В репозитории — 10, и они выведены не из головы, а из того, **кто фактически владеет колонками в таблице**: «Ответственный закупщик» в `19.20-7п`, «Руководитель» в `Telecom`, «Исполнитель (конструктор)» в `Отчет по проектам`.

Схлопывать 10 в 4 не стоит — потеряется разделение, которое в цехе уже существует: кладовщик сырья и кладовщик ГП работают с разными складами, закупщик и бухгалтер — с разными сторонами одного договора.

**Решение — развести два понятия, которые в Excel были склеены:**

```
Должность (Role)          →  что человек делает, 10 штук, привязана к людям
Право (Permission)        →  что можно с данными, ~60 штук, привязано к полям
Семейство (RoleFamily)    →  4 группы, нужны ТОЛЬКО для UI: онбординг, фильтры, навигация
```

Пользователь видит 4 понятные группы, система оперирует 60 гранулярными правами.

### 1.2. Семейства и роли

| Семейство (для UI) | Роли внутри | Смысл |
|---|---|---|
| 🟣 **Администрирование** | `admin` | Пользователи, права, справочники, аудит |
| 🔵 **Коммерция и проекты** | `sales_manager`, `accountant`, `director` | Заказы, цены, платежи, сверки, отчётность |
| 🟠 **Инженерия и производство** | `engineer`, `planner`, `shop_foreman` | Спецификации, трудочасы, план, этапы |
| 🟢 **Снабжение и склад** | `procurement`, `warehouse_material`, `warehouse_fg` | Материалы, закуп, остатки, приход/отгрузка |
| ⚪ **Наблюдатель** | `viewer` *(новая)* | Только чтение итоговых статусов; для заказчиков и смежников |

`viewer` — единственная новая роль. В исходной таблице её аналога нет, потому что в Google Sheets «только чтение» означало доступ ко всему файлу целиком, включая себестоимость.

### 1.3. Ключевая идея: группа полей = единица права = вкладка в UI

Одна абстракция закрывает три задачи разом. Сущность `Order` имеет 66 полей — вместо 66 правил вводим **5 групп**:

| Группа полей `Order` | Поля | Кто читает | Кто пишет |
|---|---|---|---|
| `core` | № заказа, заказчик, проект, регион, тип, даты | все | `sales_manager` |
| `commercial` | цена, сумма, аванс, постоплаты, штраф, остаток к оплате | коммерция, `director` | `sales_manager`, `accountant` |
| `production` | резерв, на складе, к изготовлению, срок изготовления | все кроме `viewer` | `planner`, `warehouse_fg` |
| `logistics` | № АПП, накладная, доверенность, даты отгрузки | все кроме `viewer` | `warehouse_fg` |
| `cost` | себестоимость, трудоёмкость, маржа | `engineer`, `director`, `admin` | никто (расчётное) |

Та же группировка работает как:
- **право доступа** — `order.commercial:read`, `order.commercial:write`;
- **проекция API** — сервер не отдаёт поля групп, на которые нет `:read`;
- **пресет колонок в таблице** — переключатель «Основное / Финансы / Производство / Отгрузка» из [06_SHEET_ANALYSIS_AND_DESIGN.md](06_SHEET_ANALYSIS_AND_DESIGN.md#62-реестр-заказов);
- **секция в карточке** — свёрнутый блок, если прав нет — блок просто отсутствует.

> Именно это отвечает на требование «инженер вносит трудочасы, менеджер — коммерческие условия»: они работают с одной сущностью, но с разными группами полей.

### 1.4. Схема прав (Prisma)

```prisma
enum PermissionAction { READ WRITE APPROVE }

/// Право = ресурс + группа полей + действие.
/// Код вида "order.commercial:write", "article.cost:read".
model Permission {
  id          String           @id @default(uuid()) @db.Uuid
  code        String           @unique @db.VarChar(80)
  resource    String           @db.VarChar(50)   // "order", "article", "routing"
  fieldGroup  String?          @map("field_group") @db.VarChar(50) // null = вся сущность
  action      PermissionAction
  description String?          @db.Text

  rolePermissions RolePermission[]
  @@unique([resource, fieldGroup, action])
  @@map("permissions")
}

model RolePermission {
  roleId       String  @map("role_id")       @db.Uuid
  permissionId String  @map("permission_id") @db.Uuid
  /// Ограничение видимости строк: "own" — только свои, "division" — своё подразделение, null — все.
  rowScope     String? @map("row_scope") @db.VarChar(20)

  role       Role       @relation(fields: [roleId],       references: [id], onDelete: Cascade)
  permission Permission @relation(fields: [permissionId], references: [id], onDelete: Cascade)

  @@id([roleId, permissionId])
  @@map("role_permissions")
}

/// Описание групп полей — источник правды и для API, и для UI.
/// Заполняется сидом, редактируется только админом.
model FieldGroupDefinition {
  id          String  @id @default(uuid()) @db.Uuid
  resource    String  @db.VarChar(50)
  code        String  @db.VarChar(50)
  label       String  @db.VarChar(100)   // "Финансы"
  fields      Json                        // ["unitPrice","lineTotalVat","prepayment", …]
  isCalculated Boolean @default(false) @map("is_calculated") // группа только для чтения всегда
  sortOrder   Int     @default(0) @map("sort_order")

  @@unique([resource, code])
  @@map("field_group_definitions")
}

model Role {
  // … существующие поля …
  family      String  @default("commercial") @db.VarChar(30) // для группировки в UI
  isSystem    Boolean @default(false) @map("is_system")      // admin нельзя удалить
  rolePermissions RolePermission[]
}
```

### 1.5. Как это работает на бэкенде

Два перехватчика поверх существующего `RbacGuard`:

```ts
// 1. На чтение — проекция ответа. Поля без права :read не попадают в JSON вообще.
@Injectable()
export class FieldProjectionInterceptor implements NestInterceptor {
  intercept(ctx: ExecutionContext, next: CallHandler) {
    const { user } = ctx.switchToHttp().getRequest();
    const resource = this.reflector.get(RESOURCE_KEY, ctx.getHandler());

    return next.handle().pipe(
      map((payload) => projectByPermissions(payload, resource, user.permissions)),
    );
  }
}

// 2. На запись — отсечение полей без права :write, ДО валидации DTO.
export function assertFieldWriteAllowed(
  body: Record<string, unknown>,
  resource: string,
  permissions: string[],
) {
  const denied = Object.keys(body).filter(
    (field) => !permissions.includes(`${resource}.${groupOf(resource, field)}:write`),
  );
  if (denied.length) {
    throw new ForbiddenException({
      code: 'FIELD_WRITE_FORBIDDEN',
      message: `Нет прав на изменение полей: ${denied.join(', ')}`,
      fields: denied,
    });
  }
}
```

Порядок в цепочке запроса:

```
JwtAuthGuard → RbacGuard (эндпоинт) → assertNoCalculatedFieldUpdate (уже есть)
             → assertFieldWriteAllowed (новое) → сервис → FieldProjectionInterceptor (новое)
```

**Правило, которое нельзя нарушать:** скрытие поля происходит на сервере, а не через `hidden: true` в таблице. Иначе себестоимость будет видна в DevTools у любого, кто открыл экран заказов.

### 1.6. Фронтенд получает права одним запросом

```jsonc
// GET /api/v1/auth/me
{
  "user": { "id": "…", "email": "engineer@cmk.kz", "fullName": "Жаксылык А." },
  "roles": ["engineer"],
  "family": "engineering",
  "permissions": [
    "order.core:read", "order.production:read", "order.cost:read",
    "article.cost:read", "routing:read", "routing:write",
    "bom:read", "bom:write"
  ],
  "fieldGroups": {                       // описание групп — чтобы UI строил формы сам
    "order": [
      { "code": "core",       "label": "Основное", "fields": ["orderNumber", "customerId", "…"] },
      { "code": "production", "label": "Производство", "fields": ["reservedQty", "…"] }
    ]
  }
}
```

Компонент-обёртка вместо ручных проверок в каждом месте:

```tsx
<Can I="write" a="order.commercial" fallback={<LockedField value={order.unitPrice} />}>
  <NumberInput label="Цена за ед." … />
</Can>
```

`MODULE_ACCESS` заменяется на вычисление из `permissions` — пункт меню виден, если есть хотя бы одно `:read` на его ресурсы.

Три строки, которые стоит прочитать внимательно:

- **`order.cost` закрыт для `sales_manager`.** Менеджер видит цену продажи, но не себестоимость и не маржу. В Excel это было невозможно — все колонки в одном листе.

- **`routing` пишут двое**: `engineer` задаёт норму, `shop_foreman` фиксирует факт. Это разные поля внутри группы — см. §3.

### 1.8. Ограничение по строкам (row scope)

Поля — не всё. Мастер цеха не должен видеть заказы чужого подразделения.

```ts
// Правило подмешивается в Prisma-запрос, а не фильтруется после выборки
function applyRowScope(where: Prisma.OrderWhereInput, user: UserPayload) {
  const scope = user.rowScopes['order'];
  if (scope === 'division') return { ...where, divisionId: user.divisionId };
  if (scope === 'own')      return { ...where, managerId: user.employeeId };
  return where; // null — видит всё
}
```

Для `viewer` дополнительно: `customerId = user.linkedCustomerId` — заказчик видит только свои заказы.

## 2. UX: уход от горизонтального хаоса

### 2.1. Диагноз

Что именно неудобно в исходной таблице — и чем это лечится:

| Проблема Excel | Замена в сервисе |
|---|---|
| 66–88 колонок вправо, шапка уезжает | **Пресеты колонок** (5–7 колонок) + карточка по клику |
| 44 вкладки внизу, связи неочевидны | **8 разделов** в боковом меню + «Связанные данные» в карточке |
| Формула видна только в строке ввода | **Кнопка «?» у расчётного поля** → всплывает разбор формулы |
| Правка в одном листе молча ломает другой | **Предпросмотр влияния** до сохранения |
| Один лист = одна роль, но видно всё | **Группы полей** (§1.3) |
| Фильтрация — через «Данные → Фильтр» | **Сохраняемые представления** («Мои просроченные», «Q1 Телеком») |

### 2.4. Дашборд под роль

Один URL `/dashboard`, разный состав. Инженер не видит выручку, менеджер — загрузку станков.

| Роль | Виджеты |
|---|---|
| `director` | Выручка / маржа, план-факт, дебиторка, загрузка цеха, топ-расхождения |

## 3. Модуль трудочасов (восстановление `Спецификации 2022`)

Самая ценная и самая хрупкая часть исходной книги: 40 380 формул, три передела, ручные правки построчно.

### 3.1. Что именно восстанавливаем

Из [06_SHEET_ANALYSIS_AND_DESIGN.md, §3.3](06_SHEET_ANALYSIS_AND_DESIGN.md#33-спецификации-2022--bom--калькуляция-себестоимости-42-колонки):

```
Передел                      Люди  Часы   Стоимость
Резка                          Y     Z     AA = Z×Y×ставка
Сборка / сварка / обшивка      AB    AC    AD = AC×AB×ставка
Зачистка / покраска            AE    AF    AG = AF×AE×ставка

Общ. чел/час  = (Z×Y) + (AB×AC) + (AE×AF)
Себест. труда = AA + AD + AG
Логистика     = материалы × 3 %
Вода/газ/эл.  = материалы × 1 %
Себестоимость = материалы + труд + логистика + энергия
Маржа         = себестоимость × 10 %
Цена          = себестоимость + маржа
```

Ставка 2 040 ₸/час тянулась из скрытого листа `ЗП сотр.`; проценты лежали в строке 1.

### 3.2. Модель данных

```prisma
enum RoutingStage {
  CUTTING     // Резка
  ASSEMBLY    // Сборка / сварка / обшивка
  PAINTING    // Зачистка / покраска
}

/// Норма труда по переделу. Плюс факт — для сравнения «норма vs цех».
model RoutingOperation {
  id        String       @id @default(uuid()) @db.Uuid
  articleId String       @map("article_id") @db.Uuid
  stage     RoutingStage
  sortOrder Int          @default(0) @map("sort_order")

  // Норму задаёт engineer
  workers      Decimal @db.Decimal(6, 2)
  hoursPerUnit Decimal @map("hours_per_unit") @db.Decimal(8, 3)

  // Факт фиксирует shop_foreman — те же поля, другая группа прав
  actualWorkers Decimal? @map("actual_workers")  @db.Decimal(6, 2)
  actualHours   Decimal? @map("actual_hours")    @db.Decimal(8, 3)

  workCenterId String? @map("work_center_id") @db.Uuid
  notes        String? @db.Text
  updatedAt    DateTime @updatedAt @map("updated_at")
  updatedById  String?  @map("updated_by_id") @db.Uuid

  article    Article     @relation(fields: [articleId],    references: [id], onDelete: Cascade)
  workCenter WorkCenter? @relation(fields: [workCenterId], references: [id])
  history    RoutingOperationHistory[]

  @@unique([articleId, stage])
  @@index([workCenterId])
  @@map("routing_operations")
}

/// История норм — в Excel её не было вообще, правка затирала предыдущее значение.
model RoutingOperationHistory {
  id            String   @id @default(uuid()) @db.Uuid
  operationId   String   @map("operation_id") @db.Uuid
  workers       Decimal  @db.Decimal(6, 2)
  hoursPerUnit  Decimal  @map("hours_per_unit") @db.Decimal(8, 3)
  changedAt     DateTime @default(now()) @map("changed_at")
  changedById   String?  @map("changed_by_id") @db.Uuid
  reason        String?  @db.Text

  operation RoutingOperation @relation(fields: [operationId], references: [id], onDelete: Cascade)
  @@index([operationId, changedAt])
  @@map("routing_operation_history")
}

/// Участок с собственной ставкой — вместо единой 2 040 ₸ на всё.
model WorkCenter {
  id             String  @id @default(uuid()) @db.Uuid
  code           String  @unique @db.VarChar(20)
  name           String  @db.VarChar(100)
  stage          RoutingStage
  hourlyRate     Decimal @map("hourly_rate") @db.Decimal(12, 2)
  capacityPerDay Decimal @map("capacity_per_day") @db.Decimal(8, 2) // чел/час в сутки

  operations RoutingOperation[]
  @@map("work_centers")
}
```

`CostingConfig` и `ArticleCosting` (снимок расчёта) описаны в [06_SHEET_ANALYSIS_AND_DESIGN.md, §5.4](06_SHEET_ANALYSIS_AND_DESIGN.md#54-маршрут-и-калькуляция-спецификации-2022-кол-xap).

### 3.4. Каскад пересчёта

Правило: считаем **точечно**, полный пересчёт 27 тысяч строк не запускаем никогда (см. [TZ_Cascade_RBAC.md](TZ_Cascade_RBAC.md)).

```
PATCH /articles/:id/routing/:stage
   │
   ├─ транзакция: update RoutingOperation + insert RoutingOperationHistory + AuditLogEntry
   │
   └─ очередь: recalcArticleCost(articleId)
         │
         ├─ ArticleCosting — новый снимок (старые сохраняются)
         ├─ Article.specPrice, priceDeviationPct
         ├─ если |отклонение| > порога → задача директору на пересмотр цены
         └─ WebSocket "article:cost_updated" → подписчики экранов «Прайс» и «Спецификации»
```

`approvedPrice` при этом **не меняется**. Расчёт может показать 1 011 ₸ при утверждённых 715 ₸ — прайс останется прежним до явного согласования директором.

## 4. Дизайн-система

### 4.1. Принципы

1. **Данные важнее украшений.** Тени, градиенты и скругления не должны конкурировать с цифрами.
2. **Один акцент.** Синий `#0057FF` — только для действий и активного состояния. Статусы — своя приглушённая палитра.
3. **Плотность настраивается.** Кладовщику нужны крупные элементы, плановику — 40 строк на экран.
4. **Замок объясняет, а не просто запрещает.** У заблокированного поля всегда подпись, почему.
5. **Расчётное поле выглядит иначе, чем вводимое** — на уровне фона, а не только иконки.

### 4.2. Токены

```css
:root {
  /* Нейтральные — основа интерфейса */
  --gray-0:#F8F9FA; --gray-1:#F1F3F5; --gray-2:#E9ECEF; --gray-3:#DEE2E6;
  --gray-5:#ADB5BD; --gray-6:#868E96; --gray-7:#495057; --gray-9:#212529;

  /* Акцент — только действия */
  --brand-6:#0057FF; --brand-7:#0047D4; --brand-0:#E8F0FF;

  /* Статусы — приглушённые, не кричат */
  --ok-6:#00A854;   --ok-0:#E6F7ED;
  --warn-6:#FF9500; --warn-0:#FFF8E6;
  --err-6:#E53228;  --err-0:#FFEBEA;
  --info-6:#0B7FD4; --info-0:#E7F3FC;

  /* Типографика: 6 размеров, больше не нужно */
  --fz-xs:11px;  /* подписи, метки колонок */
  --fz-sm:13px;  /* таблицы, вспомогательный текст */
  --fz-md:14px;  /* основной */
  --fz-lg:16px;  /* заголовки карточек */
  --fz-xl:20px;  /* заголовки разделов */
  --fz-2xl:28px; /* KPI-числа */

  /* Числа — только моноширинный с табличными цифрами */
  --ff-num:'JetBrains Mono', ui-monospace, monospace;
  --fvn: tabular-nums;

  --r-sm:6px; --r-md:8px; --r-lg:12px; --r-full:999px;
  --sp-1:4px; --sp-2:8px; --sp-3:12px; --sp-4:16px; --sp-6:24px; --sp-8:32px;

  /* Тени — две, и обе едва заметные */

  --sh-md:0 4px 12px rgba(16,24,40,.08);

```

**Числа в таблицах — обязательно `font-variant-numeric: tabular-nums` и выравнивание вправо.** Без этого столбец сумм «пляшет», и сравнить значения глазом невозможно — типичная болезнь дашбордов на пропорциональном шрифте.

### 4.3. Микротипографика

| Правило | Как |
|---|---|
| Разряды | `1 247 500 ₸` — неразрывный пробел, не запятая |
| Дроби | `0,330` — запятая (локаль ru-RU) |
| Валюта | символ после числа через неразрывный пробел |
| Проценты | `+15,4 %` — со знаком, с пробелом перед `%` |
| Даты в таблице | `28.04.26` компактно; в карточке — `28 апреля 2026` |
| Артикулы | моноширинный, `a-001`, без переносов |
| Пустое значение | `—` (em dash), никогда не `0` и не пусто |
| Отрицательные | `−330` (минус U+2212), красным, без скобок |

### 4.4. Статусы-теги

Точка + текст, светлая заливка, без обводки. Не полагаемся только на цвет — форма точки различается для доступности.

```
● Черновик      серый     ○ полая точка
● Подтверждён   синий     ● сплошная
● В производстве янтарный  ◐ половина
● К отгрузке    голубой   ◑ половина
● Отгружен      зелёный   ● сплошная
● Закрыт        бирюзовый ✓ галочка
● Отменён       красный   ✕ крест
⚠ Просрочка 6 дн красный   треугольник + число дней
```

### 4.5. Состояния полей — визуальный словарь

Пользователь должен различать четыре состояния, не читая подписей:

```
┌──────────────────────────────────────────────────────────────┐
│  Вводимое         Цена за ед.  [  52 300        ]  белый фон │
│                                                     ✎ курсор │
│                                                              │
│  Расчётное        Сумма с НДС  [  52 300      🔒]  серый фон │
│                   ⓘ = кол-во × цена                 [?] разбор│
│                                                              │
│  Нет прав         Себестоимость [ ●●●●●●      🔒]  штриховка │
│                   Нет доступа — роль «Менеджер»              │
│                                                              │
│  Заблокировано    Штраф        [       0      🔒]  серый фон │
│  бизнес-правилом  Меняет только бухгалтер                    │
└──────────────────────────────────────────────────────────────┘
```

Различие между «расчётное» и «нет прав» принципиально: в первом случае значение видно, но менять его бессмысленно; во втором — значение существует, но не для этого пользователя.

### 4.6. Адаптивность

| Ширина | Раскладка |
|---|---|
| ≥ 1440 | Меню + таблица + боковая панель карточки одновременно |
| 1024–1439 | Меню + таблица; карточка — оверлей справа |
| 768–1023 | Меню сворачивается в иконки; таблица — 4 колонки |
| < 768 | Таблица → список карточек; меню — выдвижное; мастера на весь экран |

На мобильном реестр заказов превращается в ленту:

```
┌────────────────────────────┐
│ П-88192-21      ● В работе │
│ КарТел · Алматы            │
│ Доп. комплектация БС       │
│ ──────────────────────────  │
│ 1 шт        52 300 ₸       │
│ План вывоза   28.04.2026   │
└────────────────────────────┘
```

### 4.7. Что убрать из текущего интерфейса

По итогам ревизии фронтенда:

- **Размытые круги (`filter: blur(140px)`)** на входе и дашборде — визуальный шум, съедают производительность на слабых машинах в цехе. Заменить на плоский фон.
- **`fontSize: 52` в заголовке входа** — избыточно; максимум 32 px.
- **Тени на карточках KPI** — достаточно рамки `1px --gray-2`.
- **Скругление `radius="xl"` на кнопках** — для делового интерфейса `--r-md` (8px) уместнее «таблеток».
- **Три вложенных `Stack` в сайдбаре** — упростить разметку.

## 5. Пошаговый план внедрения

Порядок продиктован зависимостями: права нужны раньше экранов, справочники — раньше расчётов.

### Этап 1. Фундамент прав (2–3 недели)

1. Prisma: `Permission`, `RolePermission`, `FieldGroupDefinition`, `Role.family`; роль `viewer`.
2. Сид: ~60 прав и 17 групп полей из матрицы §1.7.
3. Бэкенд: `FieldProjectionInterceptor`, `assertFieldWriteAllowed`, `applyRowScope`.
4. `GET /auth/me` отдаёт права и описание групп полей.
5. Фронтенд: `<Can>`, замена декоративного `MODULE_ACCESS` на вычисление из прав.
6. Тесты: по одному на каждую роль — «не видит того, чего не должен» (проверять **тело ответа**, а не только код 403).

**Готово, когда:** инженер, открыв заказ, не получает `unitPrice` в JSON-ответе.

### Этап 2. Справочники и оргструктура (2 недели)

`LegalEntity`, `Division`, `Project`, `Site`, `WorkCenter`, `CostingConfig`, `DealStage`, `CustomerManagerAssignment` — из [06_SHEET_ANALYSIS_AND_DESIGN.md, §5](06_SHEET_ANALYSIS_AND_DESIGN.md#5-схема-данных-prisma). Экраны CRUD под `admin`.

**Готово, когда:** менеджер по заказчику берётся из справочника, а не из `IF(K="Радикс";"Алитет";…)`.

### Этап 3. Модуль трудочасов (3 недели) ← приоритет заказчика

`RoutingOperation`, `RoutingOperationHistory`, `ArticleCosting`; калькулятор §3.3; каскад §3.4; предпросмотр влияния.

**Готово, когда:** правка часов пересчитывает себестоимость точечно, с историей и предупреждением о затронутых заказах.

### Этап 4. Заказы и реестры (3 недели)

Мастер в 4 шага, реестр с пресетами колонок, боковая карточка, раскрывающийся расчёт, сохраняемые представления.

### Этап 5. План, склад, финансы (4 недели)

План с раскладкой по неделям, приход ГП, дефицит закупа, договоры-основания, сверка «заказ ↔ ДО».

### Этап 6. Дашборды и полировка (2 недели)

Ролевые дашборды, дизайн-токены §4.2, адаптив, чистка визуального шума §4.7.

**Итого ~16 недель.** Этапы 4 и 5 частично параллелятся при двух фронтендерах.

| Права на уровне полей размазываются по коду и расходятся | Единственный источник правды — `FieldGroupDefinition` в БД; интерцептор один на все модули |
| Пользователи привыкли к «вижу всё» и воспримут ограничения как поломку | Роли включать поэтапно: сначала все видят всё + аудит, через месяц — ограничения. Блок «нет доступа» подписан, а не пуст |
| Каскад пересчёта уронит базу на массовой правке | Точечный пересчёт по `articleId`; массовые операции — только фоновой очередью; снимки `ArticleCosting` вместо пересчёта задним числом |
| Нормы труда в Excel неполные — часть артикулов без часов | Экран «Спецификации без норм» в дашборде инженера; до заполнения себестоимость помечается «неполная», а не считается заниженной |
| Внешняя книга `IMPORTRANGE` останется источником | Пока доступа нет — импорт снимком с явной датой актуальности в UI |
