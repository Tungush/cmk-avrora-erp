# ЦМК АВРОРА — синхронизация с 1С и отказ от таблиц

Документ отвечает на вопрос: **кто источник истины для каких данных** и как сервис и 1С обмениваются ими, не создавая двух конкурирующих правд.

Опирается на: [07_ARCHITECTURE_AND_UX.md](07_ARCHITECTURE_AND_UX.md), [05_DEV_ROADMAP.md](05_DEV_ROADMAP.md) (Этап 5), [06_SHEET_ANALYSIS_AND_DESIGN.md](06_SHEET_ANALYSIS_AND_DESIGN.md).

## 0. Отправная точка

В роадмапе Этап 5 был написан так, будто 1С шлёт нам вебхуки. Реальность оказалась другой и лучше: **у 1С уже есть готовые HTTP-сервисы с GET-запросами** («ТЗ для запросов GET», v10) — мы сами ходим за данными. Это меняет механику: не ждём push, а опрашиваем (pull).

Порядок внедрения: **сначала только принимаем** — заказы клиентов, счета, закуп у поставщиков. Отправка (создание заказа в 1С, заявка на номенклатуру) включается позже, инфраструктура для неё уже готова (§3).

Что уже работает и станет опорой интеграции:

| Готово в сервисе | Что даёт для 1С-обмена |
|---|---|
| Заявки на номенклатуру (`nomenclature_requests`) | Готовый процесс; осталось заменить локальное присвоение артикула на ответ 1С |
| Приход материалов с пересчётом цены и каскадом в себестоимость | Готовый приёмник документа «Поступление товаров» из 1С |
| Состав изделий: 18 141 позиция BOM на 2 160 артикулов | Данные, которых в 1С нет — наша уникальная ценность |
| Точечный каскад пересчёта + снимки `ArticleCosting` | Себестоимость считаем мы, 1С такого не умеет |
| Сверка «заказ ↔ ДО» | Шаблон для будущей сверки «сервис ↔ 1С» |
| Аудит всех изменений (`audit_log`) | Основа для разбора «кто и когда разошёлся с 1С» |

Что сейчас приходит из 1С **вручную, через Excel**: остатки ТМЦ, сырьё, бухгалтерские остатки, статусы заказов (лист `7.28`), договоры-основания с оплатами (`19.20-7п`). Это и есть та ручная синхронизация, которую надо заменить.

## 1. Главный принцип: владение по доменам, а не «одна главная система»

Требование «наш сервис — истина» нельзя понимать буквально: приход материала оформляется накладной, реализация — счётом-фактурой, и юридическую силу этим документам даёт 1С. Если объявить сервис истиной во всём, бухгалтерия начнёт вести параллельный учёт, и разойдутся обе системы.

Работающая формулировка:

> **У каждого поля ровно один владелец. Владелец пишет, второй читает и никогда не переписывает.**

Сервис — истина в том, чего в 1С физически нет и не будет: **спецификации, нормы труда, расчётная себестоимость, план производства, резервы**. 1С — истина в первичных документах и юридических реквизитах. Пересечение — узкое и разграничено явно.

Это ровно тот же приём, что уже применён для ролей в §1.3 плана: **группа полей = единица владения**. Только теперь измерение не «роль», а «система».

## 2. Матрица владения

`W` — владелец (пишет), `R` — читает копию, `—` — не имеет данных.

| Данные | Сервис | 1С | Направление | Комментарий |
|---|---|---|---|---|
| Номенклатура: наименование, серия | **W** (инициатор) | **W** (код) | ↔ | Заявку создаём мы, артикул присваивает 1С |
| Состав изделия (BOM) | **W** | — | → | В 1С спецификаций нет |
| Нормы труда, трудочасы | **W** | — | → | Только у нас |
| Расчётная себестоимость, калькуляция | **W** | — | → | 1С считает по факту, мы — по норме |
| Утверждённая цена (прайс) | **W** | R | → | Меняется решением директора у нас |
| Заказ клиента: шапка, состав | R *(этап 1)* | **W** | ← | Сейчас принимаем из 1С; создание с нашей стороны — следующий этап |
| Заказ клиента: оплаты, реализация | R | **W** | ← | Первичка и деньги — 1С |
| Заказ поставщику (снабжение) | R | **W** | ← | Снабжение работает в 1С |
| Приход материалов: кол-во, цена | R | **W** | ← | Накладная — документ 1С |
| Учётная цена материала (средневзвешенная) | **W** | R | → | Считаем мы из приходов, для себестоимости |
| Остатки складов (бухгалтерские) | R | **W** | ← | Сверяем со своими |
| Резерв под заказ, «к изготовлению» | **W** | — | → | Планирование — наше |
| Факт выпуска продукции | **W** | R | → | Цех подтверждает у нас → списание сырья в 1С |
| Отгрузка: факт | R | **W** | ← | Реализация — документ 1С |
| Контрагенты, БИН/ИИН, договоры | R | **W** | ← | Юридические реквизиты |

Два места требуют особого внимания, потому что там владение делится **внутри одной сущности**:

**Номенклатура.** Мы владеем смыслом (что это за изделие, из чего состоит, сколько труда), 1С владеет идентификатором (артикул/код). Поэтому поток двухтактный: заявка → присвоение → обогащение.

**Заказ клиента.** Шапку и состав создаём мы (менеджер работает в удобном мастере, а не в 1С). Как только 1С оформила документ — деньги и реализация принадлежат ей, мы их только читаем. Граница проходит ровно по группам полей `order.core`/`order.production` (наши) против `order.commercial`/`order.logistics` (факты из 1С).

## 3. Механика обмена

### 3.1. Слой изоляции (Anti-Corruption Layer)

Ядро сервиса не должно знать о существовании 1С. Между ними — модуль `integration/1c`, который переводит наши сущности в объекты 1С и обратно.

```
Ядро (orders, articles, warehouse)
        │  доменные события / команды
        ▼
Интеграционный слой (ACL)
   ├── маппинг ID       ExternalRef
   ├── исходящие        Outbox → воркер → 1С
   ├── входящие         1С → Inbox → обработчик
   └── контракты        DTO 1С, отдельно от наших моделей
        ▼
1С:Предприятие (HTTP-сервис / OData)
```

Смысл: когда в 1С переименуют реквизит или изменят версию конфигурации, правится один адаптер, а не двадцать мест в коде.

### 3.2. Три новые таблицы

```prisma
/// Соответствие «наш объект ↔ объект внешней системы».
/// Без него любая повторная выгрузка создаёт дубли.
model ExternalRef {
  id           String   @id @default(uuid()) @db.Uuid
  entityType   String   @db.VarChar(50)   // "Article" | "Order" | "Material" | "Customer"
  localId      String   @db.Uuid
  system       String   @db.VarChar(20)   // "1C"
  externalId   String   @db.VarChar(64)   // GUID объекта в 1С
  externalCode String?  @db.VarChar(50)   // код/номер, человекочитаемый
  syncedAt     DateTime @updatedAt
  payloadHash  String?  @db.VarChar(64)   // чтобы не гонять неизменившееся

  @@unique([system, entityType, localId])
  @@unique([system, entityType, externalId])
}

/// Исходящие сообщения. Пишутся в той же транзакции, что и само изменение —
/// иначе при падении сети заказ создан, а в 1С не ушёл (и никто не заметил).
model OutboxMessage {
  id          String    @id @default(uuid()) @db.Uuid
  type        String    @db.VarChar(50)   // "order.created" | "nomenclature.requested" | "production.completed"
  entityType  String    @db.VarChar(50)
  entityId    String    @db.Uuid
  payload     Json
  status      String    @default("PENDING") @db.VarChar(20) // PENDING|SENT|FAILED|DEAD
  attempts    Int       @default(0)
  lastError   String?   @db.Text
  createdAt   DateTime  @default(now())
  sentAt      DateTime?

  @@index([status, createdAt])
}

/// Входящие. Сначала сохраняем сырьё, потом обрабатываем —
/// повторная доставка того же externalKey не должна применяться дважды.
model InboxMessage {
  id          String   @id @default(uuid()) @db.Uuid
  system      String   @db.VarChar(20)
  type        String   @db.VarChar(50)   // "receipt.posted" | "payment.posted" | "stock.snapshot"
  externalKey String   @db.VarChar(120)  // GUID документа 1С
  payload     Json
  status      String   @default("NEW") @db.VarChar(20) // NEW|PROCESSED|FAILED|IGNORED
  error       String?  @db.Text
  receivedAt  DateTime @default(now())
  processedAt DateTime?

  @@unique([system, type, externalKey])
}
```

### 3.3. Гарантии

| Проблема | Решение |
|---|---|
| Сеть упала после сохранения заказа | Outbox в одной транзакции с заказом; воркер дошлёт |
| 1С прислала документ дважды | `@@unique([system, type, externalKey])` — второй раз игнорируется |
| 1С недоступна 2 часа | Ретраи с экспоненциальной задержкой, после N попыток — `DEAD` + алерт ответственному |
| Мы и 1С поменяли одно поле одновременно | Владелец поля из §2 выигрывает; чужое изменение пишется в расхождения, а не применяется молча |
| Массовая выгрузка остатков | Не событие, а снимок по расписанию + сверка, см. §5 |

### 3.4. Что реализовано (Этап 1)

| Элемент | Где |
|---|---|
| Модели `ExternalRef`, `OutboxMessage`, `InboxMessage` | `schema.prisma` |
| Сервис обмена: enqueue в транзакции, ретраи 1→16 мин, HMAC | `services/integration.service.ts` |
| Обработчики входящих: номенклатура, приход, снимок остатков | `modules/integration/inbox-handlers.service.ts` |
| Вебхук `POST /integrations/1c/{тип}` + журнал | `modules/integration/integration.controller.ts` |
| Экран «Обмен с 1С» | `pages/Integration` |
| Приход как общий сервис (ручной ввод и 1С — одна логика) | `services/material-receipt.service.ts` |

Настройка: `INTEGRATION_1C_URL` (адрес HTTP-сервиса 1С) и `INTEGRATION_1C_SECRET` (общий секрет для HMAC). Пока адрес не задан — исходящие копятся в `PENDING`, входящие уже принимаются.

### 3.5. Транспорт

Рабочий вариант для типовой 1С:
- **входящие** — HTTP-сервис 1С шлёт `POST /api/v1/integrations/1c/{type}` с HMAC-подписью (как уже заложено в [04_ROLES_PERMISSIONS.md](04_ROLES_PERMISSIONS.md), §вебхуки — подпись, не JWT);
- **исходящие** — наш воркер зовёт HTTP-сервис 1С; если его написать нельзя, запасной путь — OData `/odata/standard.odata/Document_ЗаказПокупателя`.

Выбор между HTTP-сервисом и OData — вопрос к 1С-подрядчику: OData даёт чтение «из коробки», но запись через него хрупкая (нет бизнес-логики проведения документа).

## 3.6. Канал приёма: GET-запросы к 1С

1С отдаёт данные четырьмя HTTP-сервисами. Все они **точечные**: принимают номер конкретного документа.

| Запрос | Что отдаёт | Путь | Ключи |
|---|---|---|---|
| **GET A** | Заказ клиента: шапка, номенклатура, оплаты | `/erp/hs/fm/orders` | `clientorder_num`+`clientorder_year` или `clientorder_adem` |
| **GET B** | Счета и акты по заказу | `/erp/hs/fm/invoices` | `invoice_num`+`invoice_year` |
| **GET C** | Заказ поставщику: закуп, оплаты, закрывающие документы, взаимозачёты | `/erp/hs/TurnOver/v1/get_c` | `supplier_invoice_num`+`year` или `supplier_invoice_adem` |
| **GET D** | Обороты: какие заказы поставщику идут под заказ клиента | `/erp/hs/TurnOver/v1/get_d` | `clientorder_num`+`year` или `clientorder_adem` |

### Ключ связи: два формата номеров

В нашей базе, унаследованной из Google Sheets, уживаются оба формата — и оба нужны:

| Формат | Сколько | Как ищем в 1С |
|---|---|---|
| `П-100014-22` | 1 652 | по `clientorder_adem` — прежняя система |
| `Т7АА-002345-2026`, `АСАА-005959-2025` | 75 | разбираем на `clientorder_num` + `clientorder_year` |
| `TC-ROW104`, `DP-ROW102` | 439 | номера придуманы импортом, в 1С их нет — пропускаем |

Разбор делает `parseOrderNumber` (`onec-client.service.ts`): последняя группа из четырёх цифр — год, значит это номер 1С; иначе — «адемовский».

### Стратегия при точечном доступе

Списка «что изменилось с даты» в ТЗ нет, поэтому синхронизация обходит **номера, которые мы уже знаем**:

```
активные заказы у нас (по дате последней синхронизации, старые — первыми)
   → GET A по каждому → шапка, статус, суммы, оплаты, строки
   → GET D по каждому → номера заказов поставщику
      → GET C по каждому → закуп: суммы, оплаты, поставщик
```

Ограничение честное и важное: **заказ, заведённый в 1С и неизвестный нам, так не появится**. Это первый вопрос к 1С-подрядчику (§9).

### Что перезаписываем, а что нет

| Поле из 1С | Действие |
|---|---|
| Контрагент, БИН | Upsert по БИН; наш дубль по имени дозаполняется |
| Статус заказа | Маппинг «На согласовании→DRAFT, К выполнению→CONFIRMED, Закрыт→CLOSED». **Если заказ у нас в производстве, статус 1С «К выполнению» его не откатывает** |
| Даты, регион, проект, подразделение | Перезаписываем |
| Строки: количество, цена, сумма | Перезаписываем; **резерв и отгрузка остаются нашими** |
| Суммы и оплаты 1С | В отдельные поля `onecTotalAmount` / `onecPaidAmount` — не смешиваются с нашими расчётными |
| Артикул из строки, которого у нас нет | **Не создаём молча** — попадает в отчёт «неизвестная номенклатура» |
| Незнакомый статус | Не двигает заказ, попадает в отчёт |

Реализация: `modules/integration/onec-sync.service.ts`, эндпоинты `POST /integrations/1c/sync/orders`, `…/sync/order/{номер}`, `…/sync/procurement/{номер}`, проверка связи `GET /integrations/1c/ping`.

Настройка: `ONEC_BASE_URL` (адрес из «Лист3» ТЗ — `http://10.10.10.81`), `ONEC_LOGIN`, `ONEC_PASSWORD`, `ONEC_TIMEZONE` (по умолчанию `Asia/Almaty`).

### Отладка без доступа к 1С

Боевой `10.10.10.81` — внутренний адрес; снаружи корпоративной сети он недоступен. Чтобы не ждать доступа, в репозитории есть мок тех же четырёх сервисов:

```bash
npm run mock:1c                                   # поднимает http://localhost:8081
ONEC_BASE_URL=http://localhost:8081 npm run start:dev
```

Мок отдаёт данные той же формы, что и ТЗ, включая специально «неудобные» случаи: дату в формате `Wed May 13 2026 05:00:00 GMT+0500`, артикул, которого нет в нашей базе, и пустой ответ на номера вида `TC-ROW…`.

**Что уже проверено на моке:** разбор обоих форматов номера, кириллица в query, маппинг шапки и строк, защита статуса производства, цепочка «заказ клиента → GET D → GET C → закуп в `payment_documents`».

**Найдено и исправлено при отладке:** 1С отдаёт даты без часового пояса (`2026-09-30T00:00:00`), из-за чего план вывоза записывался на сутки раньше. Теперь календарная дата сохраняется как UTC-полночь и не зависит от пояса сервера.

## 4. Потоки

### 4.1. Заявка на номенклатуру (у нас → 1С → у нас)

Уже работает локально; меняется только шаг присвоения кода.

```
Инженер: «нет артикула» → заявка (сервис)
   → outbox: nomenclature.requested
      → 1С: создать элемент справочника «Номенклатура»
         → ответ: код + GUID
            → сервис: создан артикул, ExternalRef, карточка изделия
               → инженер заполняет состав и нормы (этого в 1С нет)
```

Пока интеграции нет — присваиваем код сами по серии (`k-033`), и это **осознанный временный режим**: при подключении 1С коды сверяются один раз и дальше приходят оттуда.

### 4.2. Заказ клиента (у нас → 1С)

```
Менеджер: мастер в 4 шага (сервис) → заказ DRAFT
   → подтверждение → outbox: order.created
      → 1С: «Заказ покупателя»
         → ответ: номер 1С + GUID → ExternalRef
Далее 1С шлёт нам: оплаты, реализацию, отгрузку → группы commercial/logistics
```

Наш номер (`П-88192-21`) остаётся человеческим ключом, номер 1С хранится рядом — как уже сделано для `bitrixDealId`.

### 4.3. Снабжение: заказ поставщику (1С → у нас)

Это ответ на «видеть, что снабжение заказало ко мне в сырьё по какой цене».

```
1С: «Заказ поставщику» проведён
   → inbox: purchase_order.posted
      → сервис: позиции + цены + ожидаемая дата + связь с заказом клиента
         → экран «Снабжение»: что едет, почём, под какой заказ
```

Ключевое: 1С в заказе поставщику указывает «заказ покупателя» — эта связка даёт цепочку **заказ клиента → закуп → приход → производство**, которой сейчас нет ни в таблицах, ни в сервисе.

### 4.4. Приход сырья (1С → у нас)

```
1С: «Поступление товаров и услуг» проведено
   → inbox: receipt.posted
      → сервис: движение прихода (уже реализовано)
         → учётная цена = средневзвешенная
            → каскад: lineCost составов → себестоимость изделий → снимок
               → SSE: экраны «Спецификации» и «Прайс» обновляются live
```

Механика прихода уже работает — проверено: приход 500 м по 420 ₸ поднял себестоимость 120 изделий. Останется заменить ручной ввод на сообщение из 1С, оставив ручной как резервный.

### 4.5. Выпуск продукции (у нас → 1С)

```
Цех: этап «Готово» (сервис)
   → outbox: production.completed { articleId, qty, orderId }
      → 1С: «Отчёт производства за смену»
         + списание сырья по нашему BOM (норма × количество)
```

Здесь сервис — единственный источник: только у нас есть состав изделия, по которому 1С сможет списать сырьё.

### 4.6. Остатки (1С → у нас, по расписанию)

Не событие, а снимок: ночью — полный, днём — по изменившимся. Наши остатки не перезаписываются молча: расхождение попадает в отчёт сверки.

## 5. Расхождения: доверять, но сверять

Две системы всегда разойдутся — вопрос в том, заметим ли мы это. Нужен экран сверки (шаблон уже есть — «заказ ↔ ДО»):

| Сверка | Что сравниваем | Что делать при расхождении |
|---|---|---|
| Остатки сырья | наш `stockQty` ↔ остаток 1С | Расход в производство мы могли не провести — показать позиции |
| Заказы | наши статусы ↔ статусы 1С | Заказ закрыт в 1С, но у нас в производстве — сигнал менеджеру |
| Оплаты | наш `balanceDue` ↔ долг 1С | Платёж не долетел — повторить обработку inbox |
| Номенклатура | наши артикулы ↔ справочник 1С | Кто-то завёл номенклатуру мимо заявки |
| Цены закупа | учётная у нас ↔ последние накладные | Приход не долетел |

Правило: **расхождение — это задача человеку, а не автоматическая перезапись.** Молчаливая перезапись — то, из-за чего в Excel никто не понимал, откуда взялась цифра.

## 7. Этапы

Порядок продиктован зависимостями: справочники раньше документов, чтение раньше записи.

| Этап | Содержание | Результат |
|---|---|---|
| **0. Данные** ✅ | Нормы труда импортированы; остаются даты заказов и привязка ДО | Себестоимость считается полностью |
| **1. Каркас** ✅ | `ExternalRef`, `Outbox`, `Inbox`, HMAC, экран «Обмен с 1С» | Инфраструктура готова; заявки и заказы уже кладут события в outbox |
| **2. Чтение из 1С** | Номенклатура (сверка кодов), контрагенты, остатки, приходы | Видно, что пришло и почём — без риска что-то сломать в 1С |
| **3. Запись в 1С** | Заявка на номенклатуру, заказ клиента | Сервис становится инициатором |
| **4. Производство** | Выпуск → списание сырья по BOM | Замыкается цикл |
| **5. Сверки** | Экраны расхождений по §5 | Две системы под контролем |
| **6. Отключение листов** | По критериям §6 | Excel уходит из процесса |

Этапы 2 и 3 разделены намеренно: сначала мы только читаем и убеждаемся, что маппинг верный, и лишь потом начинаем писать в чужую систему.

## 8. Риски

| Риск | Смягчение |
|---|---|
| В 1С нельзя написать HTTP-сервис (типовая на поддержке) | Резерв: OData на чтение + файловый обмен на запись; решается с 1С-подрядчиком на старте |
| Номенклатура в 1С и у нас разойдётся по наименованиям | Сверка справочников — первый же поток Этапа 2, до любой записи |
| Двойной ввод: менеджер создаёт заказ и у нас, и в 1С | Явный регламент: заказ создаётся **только** в сервисе; в 1С он появляется сам |
| 1С-подрядчик занят / сроки | Все потоки имеют ручной режим (как сейчас приход) — сервис работает и без интеграции |
| Расхождение «кто владеет полем» на практике | Матрица §2 — часть договорённости с бухгалтерией, а не только техническое решение |

## 9. Открытые вопросы к 1С-подрядчику

1. **Как узнать о новых заказах?** GET-запросы точечные — по номеру. Нужен эндпоинт «список заказов, изменённых с даты X» (хотя бы номера), иначе заказ, заведённый в 1С, у нас не появится, пока номер не принесут вручную.
2. **Авторизация.** Сейчас клиент умеет Basic (`ONEC_LOGIN`/`ONEC_PASSWORD`). Так и есть, или нужен токен?
3. **Лимиты.** Сколько запросов в минуту выдержит `10.10.10.81`? От этого зависит размер пакета синхронизации (сейчас 50 заказов за прогон).
4. **Сеть.** `10.10.10.81` — внутренний адрес. Сервис будет в той же сети или нужен доступ извне?
5. **`clientorder_adem`** — это ровно тот номер, что у нас в базе (`П-100014-22`)? Проверяли на выборке форматов, совпадает, но подтвердить стоит.
6. **Единицы измерения** в строках заказа клиента (GET A) — есть ли поле? Сейчас проставляем «шт» по умолчанию.
7. **Что делать со строками, где артикул не заведён у нас?** Сейчас — в отчёт. Заводить автоматически или ждать заявку на номенклатуру?
