# ЦМК АВРОРА — ERP планирования производства

Веб-сервис вместо Google-таблицы на 44 листа: заказы, спецификации с трудочасами и себестоимостью, план производства, склад, финансы. Права — на уровне групп полей. Идёт переход на приём данных из 1С.

**Стек:** NestJS + Prisma + PostgreSQL · React + Vite + Mantine · TypeScript.

---

## Быстрый старт

Нужны Docker Desktop и Node 20+.

```bash
npm run install:all              # зависимости корня, backend, frontend
cp backend/.env.example backend/.env
npm run dev                      # Postgres в Docker + backend :3000 + frontend :5173
```

Вход — любой email и роль из списка (демо-режим). Swagger: `http://localhost:3000/api/v1/docs`.

> **Node 25:** если сборка фронтенда падает на «Cannot find native binding», доустановите бинарники:
> `npm i -D @rolldown/binding-darwin-arm64 lightningcss-darwin-arm64 @tailwindcss/oxide-darwin-arm64`

## Наполнение данными

`npm run dev` уже накатывает схему и сид (роли, права, участки, коэффициенты). Исторические данные из Excel — отдельными командами **в этом порядке**:

```bash
cd backend

# 1. Полная копия книги: 44 листа, 103 842 строки, заказы, артикулы, заказчики
NODE_OPTIONS="--max-old-space-size=8192" npm run migrate:full

# 2. Материалы, составы изделий (BOM) и нормы труда из «Спецификации 2022»
npm run migrate:bom

# 3. Приходы металла с ценами из «База сырья (металл)»
npm run migrate:receipts

# 4. Договоры-основания из «19.20-7п»
npm run migrate:payment-docs
```

Что получится: 2 160 артикулов · 3 147 материалов · 18 141 позиция состава · 3 866 норм труда · 2 202 заказа · 4 682 ДО.

Импорты идемпотентны — повторный запуск не создаёт дублей и не затирает ручные правки инженера.

## Подключение к 1С

Данные принимаем **GET-запросами** к HTTP-сервисам 1С (спецификация — [docs/ТЗ_1С_запросы_GET_v10.xlsx](docs/ТЗ_1С_запросы_GET_v10.xlsx), архитектура — [08_INTEGRATION_1C.md](08_INTEGRATION_1C.md)).

```bash
# backend/.env
ONEC_BASE_URL="http://10.10.10.81"
ONEC_LOGIN="…"
ONEC_PASSWORD="…"
ONEC_TIMEZONE="Asia/Almaty"
```

Проверка и запуск синхронизации:

```bash
# связь есть?
curl -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/v1/integrations/1c/ping"

# один заказ (номер URL-кодируется, кириллица поддерживается)
curl -X POST -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/v1/integrations/1c/sync/order/%D0%9F-88192-21"

# пакетом: активные заказы, начиная с самых давно не синхронизированных
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"limit":50}' "http://localhost:3000/api/v1/integrations/1c/sync/orders"

# закуп под заказ: GET D → GET C → payment_documents
curl -X POST -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/v1/integrations/1c/sync/procurement/%D0%9F-88192-21"
```

Состояние обмена — экран **«Обмен с 1С»** в меню (роль `admin` или `director`).

### Отладка без корпоративной сети

`10.10.10.81` доступен только изнутри контура. Вне его — мок тех же четырёх сервисов:

```bash
cd backend && npm run mock:1c                      # http://localhost:8081
ONEC_BASE_URL=http://localhost:8081 npm run start:dev
```

## Что делать дальше

### Шаг 1. Проверить связь с реальной 1С

На машине внутри корпоративной сети:

1. Прописать `ONEC_BASE_URL`, `ONEC_LOGIN`, `ONEC_PASSWORD` в `backend/.env`.
2. Дёрнуть `/integrations/1c/ping` — он возьмёт первый реальный номер заказа из базы.
3. Если ответ пришёл — сравнить **фактическую структуру JSON** с ожидаемой.

Сравнить проще всего так: выполнить в браузере ссылку из листа «Лист3» ТЗ и сопоставить с моком (`backend/tools/mock-1c-server.js`).

**Где структура угадана:** в GET A массив строк номенклатуры не имеет имени поля в ТЗ. Код перебирает известные варианты (`items`, `item_alldata`, `item_data`, `lines`, `nomenclature`) и дополнительно ищет любой массив, у элементов которого есть `item_code`. Если не нашёл — заказ **не** помечается синхронизированным, а в отчёт попадает `linesNotParsed` со списком ключей ответа: по нему сразу видно, как 1С на самом деле назвала массив. Добавить имя — в `ITEM_ARRAY_KEYS` (`onec-sync.service.ts`).

Сырые ответы 1С запоминаются (последний по каждому пути) — посмотреть можно через `OneCClientService.getLastRaw()`.

### Шаг 2. Синхронизировать заказы

```bash
# сначала на одном заказе, посмотреть отчёт
POST /integrations/1c/sync/order/{номер}
# затем пакетами
POST /integrations/1c/sync/orders  {"limit": 50}
```

Отчёт вернёт расхождения, которые нужно разобрать с коллегами:

| Поле отчёта | Что значит |
|---|---|
| `notFound` | Документа нет в 1С ни по одному варианту номера |
| `missingLocally` | В 1С есть, у нас нет — заказ надо завести |
| `linesNotParsed` | Ответ пришёл, но массив строк не распознан — покажет ключи JSON |
| `unparsed` | Значения, которые не удалось разобрать (в БД не записаны) |
| `unknownArticles` | Артикулы из 1С, которых нет в нашей номенклатуре |
| `unknownStatuses` | Статусы 1С без маппинга — заказ не сдвинут |

Ни одно из этих состояний **не пишет в базу мусор**: при нераспознанной структуре заказ остаётся в очереди на следующий прогон, неразобранные числа не затирают существующие значения.

### Шаг 3. Ответить на вопросы 1С-подрядчику

Полный список — в [08_INTEGRATION_1C.md §9](08_INTEGRATION_1C.md). Блокирующий:

> **Как узнать о новых заказах?** Все четыре GET-запроса точечные — по номеру документа. Списка «что изменилось с даты X» нет, поэтому заказ, заведённый в 1С, у нас сам не появится. Нужен эндпоинт, отдающий хотя бы номера заказов за период.

### Шаг 4. Отправка данных в 1С

Инфраструктура готова (outbox с гарантией доставки, HMAC, ретраи, журнал). Заявка на номенклатуру и создание заказа уже кладут события в очередь. Осталось получить от подрядчика адрес приёмника и включить `INTEGRATION_1C_URL`.

### Известные пробелы данных

| Пробел | Сколько | Что делать |
|---|---|---|
| Активные заказы без плановой даты | 247 | Заполнить или подтянуть из 1С (`workplandate`) |
| ДО без привязки к заказу | 2 660 | Связать через GET C (`clientorder_num` в строках) |
| Артикулы без состава | 462 | Заполнить в «Спецификации → Материалы» |
| Артикулы без норм труда | ~485 | Заполнить в «Спецификации → Трудозатраты» |
| Этапы производства не отмечаются | 199 заказов на первом этапе | Процесс: мастер отмечает этапы на экране «Цех» |

## Структура

```
backend/
  prisma/          схема, сиды, импортёры Excel (migrate:*)
  src/
    common/        RBAC на уровне полей, проекция ответов, фолбэки
    modules/       контроллеры по доменам + integration/ (обмен с 1С)
    services/      себестоимость, каскад пересчёта, state machine, клиент 1С
  tools/           мок HTTP-сервисов 1С
frontend/src/
  pages/           Заказы, Спецификации, План, Цех, Склад, Финансы, Обмен с 1С
  components/      таблицы, статусы, виджеты дашборда
  hooks/ api/      react-query поверх axios
```

Тесты: `cd backend && npm test` (80 тестов, включая e2e полного цикла заказа).

## Проверить перед продом

- `JWT_SECRET`, `INTEGRATION_1C_SECRET`, пароль Postgres — сейчас dev-дефолты в коде и `docker-compose.yml`, задать через окружение.
- Демо-вход пускает по любому email — заменить на реальную аутентификацию.
- SQL-вью применяются сидом (`views.seeder.ts`), а не миграцией: `prisma migrate deploy` их не создаст.
