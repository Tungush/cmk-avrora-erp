## 1. Карта взаимосвязей данных (Data Flow / ERD Concept)

### 1.1 Сквозная цепочка (production data flow)

```
Артикулы (master ГП)
   │  Артикул (a-001), Наименование, Тоннаж/ед, Себестоимость
   ▼
Прайс / Прайс 2024  ──(Арт.)──►  Минимальные остатки
   │  УТВ цена, Цена специф., Разница=УТВ-Специф.        │  Нужно изготовить, Готовность %
   │                                                       │
   ▼                                                       ▼
Спецификации 2022 (BOM) ◄──(Артикул=col B)── План ──►  На закуп
   │  Расход на ед., VLOOKUP в 'База сырья'               │  qty*price - остаток на складе
   │  трудозатраты (Резка/Сборка-сварка/Покраска)          │
   ▼                                                       ▼
База сырья (сырьё, ИМПОРТИРУЕТСЯ извне!)  ──►  Приход ГП / Склад ГП ──► Долги по отгрузкам
```

### 1.2 Формулы-связки (ключи объединения листов)

| Откуда → Куда | Формула (дословно из файла) | Ключ связи |
|---|---|---|
| `Спецификации 2022`!E6 → `База сырья` | `=VLOOKUP(F6,'База сырья'!$E:$AA,17,FALSE)` | Артикул материала (col F) |
| `Спецификации 2022`!I6 → `План` | `=IFERROR(VLOOKUP(B6,'План'!C:Z,5,FALSE)*G6,"")` | Артикул изделия (col B = "k-001") × норма расхода |
| `Спецификации 2022`!L6 → `План` | `=VLOOKUP(C6,'План'!D:G,4,FALSE)*K6` | Наименование изделия |
| `Спецификации 2022`!O6 (вес ед.) | `=IFS(H6="м",VLOOKUP(F6,'База сырья'!E:W,19,FALSE), H6="кг",G6, ...)` | ветвление по ед.изм. |
| `Спецификации 2022`!AJ5 (з/п) | `=W5*$AJ$1`, где `AJ$1 = 'ЗП сотр.'!N9` через `План`!J1 | глобальная ставка часа |
| `Минимальные остатки`!C5 → `Прайс` | `='Прайс'!C3` / `='Прайс'!D3` | Артикул, Наименование |
| `Минимальные остатки`!G5 → `Склад ГП` | `=VLOOKUP($C5,'Склад ГП'!$B:$V,8,FALSE)` | Артикул |
| `Минимальные остатки`!J5 → `Telecom` | `SUMIFS(Telecom!$D:$D,Telecom!$B:$B,План!$C6,Telecom!$AT:$AT,$D$2)` | Артикул + период (AT) |
| `Склад ГП`!J3 → `Приход ГП` | `=SUMIFS('Приход ГП'!$L:$L,'Приход ГП'!$C:$C,$I3,'Приход ГП'!$F:$F,H3)` | Артикул + месяц |
| `Склад ГП`!K4 → `Telecom` | `=SUMIFS(Telecom!$AK:$AK,Telecom!$AS:$AS,$H4,Telecom!$AQ:$AQ,$I4)` | месяц + год |
| `Долги по отгрузкам`!C3 → `Др проекты` | `SUMIFS('Др проекты'!AC:AC, ...M:M,B3, ...BK:BK,"Да")` | Заказчик + флаг "оплачено/да" |
| `Рабочее время`!E2 → `Годовое время` | `=VLOOKUP($G$2,'Годовое время'!A:K,5,FALSE)` | Месяц |
| `Тех-лист`!A4 → `Telecom` (dropdown-источник) | array-формула `INDEX/MATCH/COUNTIF` — эмуляция `UNIQUE()` | генерация справочника артикулов для валидации |
| `База сырья` — весь лист | `=IFERROR(__xludf.DUMMYFUNCTION("IMPORTRANGE(""https://docs.google.com/...820784582"",""База Сырья!B2:B"")"),1.0)` | **внешний источник правды вне файла** |

**Критично:** `IMPORTRANGE` на `База сырья` означает, что реальный мастер-справочник сырья (цены, остатки) ведётся в отдельной Google-таблице, а текущий файл — лишь зеркало. Это первый кандидат на "единый источник правды" при миграции — иначе после переезда в БД синхронизация оборвётся.

### 1.3 Primary Source vs Calculated

| Тип | Поля |
|---|---|
| **Primary (ручной ввод)** | `Артикулы`: Артикул, Наименование, вес; `Спецификации 2022`: состав BOM (материал, норма расхода на ед.), трудозатраты (часы/чел. по операциям); `Прайс`: УТВ цена (утверждённая, вручную); `План`: Доп.Заявка; `База сырья`: закупочная цена, остаток по 1С (в исходнике — внешний импорт); `Приход ГП`, `Telecom`/`Др проекты`: факты приёмки/отгрузки/сделки; `ЗП сотр.`: список сотрудников, статус, оклад; `Рабочее время`/`Годовое время`: календарь |
| **Calculated (формулы)** | Себестоимость, Цена специф., Разница/Дешевле/Дороже, Расход на план (норма×план), Сумма (qty×price), Готовность плана %, Нужно изготовить, Кол-во на закуп, все `SUBTOTAL`/`SUM`/`SUMIFS` итоги, остатки (`=J-K`), Долги, Себестоимость трудозатрат |

## 2. UX и интерфейс ввода

### 2.1 Ручной ввод vs авторасчёт (по листам)

| Лист (аналог) | Вводит пользователь | Считает бэкенд |
|---|---|---|
| Артикулы | код, наименование, вес | — |
| Спецификации (BOM) | состав материалов, норма расхода, трудозатраты | стоимость BOM, вес ГП, себестоимость |
| Прайс | УТВ цена (после Approve) | цена по спецификации, разница, маржа |
| План | доп.заявка на период | план+мин.остатки, месячные/недельные суммы (`SUBTOTAL`→агрегаты по фильтру заменяются на GROUP BY на бэке) |
| Минимальные остатки | период расчёта (мес.) | остаток, дефицит, % готовности |
| База сырья | закупочная цена, приход | остаток (сумма движений) |
| На закуп | — (полностью производный лист) | план − остаток на складе |
| Склад ГП / Приход ГП | факт производства/приёмки (партия, дата) | остаток по месяцам |
| Telecom / Др проекты | заказ, отгрузка, статус сделки | долги, потребность |
| ЗП сотр. / Рабочее время | список сотрудников, статус, календарь | ставка часа, фонд ЗП |

### 2.2 Grid-интерфейс без поломки связей
- Формулы (`VLOOKUP`, `SUMIFS`) переносятся **на бэкенд** как computed fields — пользователь никогда не редактирует ячейку-формулу; UI показывает вычисляемые колонки как read-only (серый фон, замок-иконка), как в Airtable/Notion-таблицах, а не как в сыром Excel.
- Grid на **AG Grid / TanStack Table** с server-side pagination (листы по 3–27 тыс. строк — `Спецификации 2022` 27662 строк, `Telecom` 15140 строк — не грузить целиком в браузер).
- Строки-агрегаты (`=SUBTOTAL(9,...)` на `План`, `На закуп`, `Прайс`) → закреплённая pinned-row с серверным `SUM`/`GROUP BY` вместо клиентского пересчёта.

### 2.3 Валидации ввода
- Уникальность `Article.articleCode` (constraint в БД, как уже есть в Prisma-схеме — `@unique`).
- Dropdown-справочники — сейчас эмулируются костылём (`Тех-лист` с CSE-массив-формулой `INDEX/MATCH/COUNTIF` для получения уникальных значений из `Telecom`). В новой системе — обычные lookup-таблицы (`MaterialCategory`, `OperationType`, справочник артикулов) с `<select>`/autocomplete.
- Числовые поля (норма расхода, вес, цена) — `min:0`, тип `Decimal`, запрет текста.
- Единицы измерения (`ед.` в BOM: м/м²/кг/л/шт/пара/м³) — enum, не свободный текст (в исходнике это строка → источник ошибок в `IFS`-ветвлении).

### 2.4 Совместный доступ vs подтверждение шага
| Зона | Режим |
|---|---|
| BOM/Спецификации, План (черновик) | **realtime co-editing** (несколько технологов правят разные артикулы одновременно) — построчный lock по `articleId`, не по листу целиком |
| Прайс: УТВ цена | **workflow approval** — draft (расчётная цена) → отправлено на утверждение → Approved (роль Финансист/Руководитель) |
| Спецификации после публикации Плана | **soft lock**: правка возможна, но с версионированием (см. 2.5) |
| Приход ГП / Приход сырья | форма ввода факта, без конкурентного редактирования (append-only журнал движений) |

### 2.5 Каскад изменений первичных данных
Сейчас в Excel изменение состава BOM **мгновенно и необратимо** пересчитывает все связанные формулы, включая уже прошедшие периоды (`Расход на план` тянет текущий `План` без разделения на "было на момент запуска" и "сейчас"). Это системный риск исходника.

Решение для новой системы:
1. `BomItem` — **версионируется** (`validFrom`/`validTo` или отдельная `BomVersion`), как уже частично заложено паттерном `PriceHistory`.
2. `ProductionPlanItem` при формировании плана делает **снапшот** нормы расхода на момент расчёта (не живую ссылку на BOM) — аналог "заморозки" строки заказа.
3. Изменение BOM **не** каскадирует на `CLOSED`/`SHIPPED` заказы и на уже сформированные `PurchaseRequest`; пересчёт затрагивает только периоды в статусе `DRAFT`/будущие.
4. Любое изменение BOM/цены — запись в `AuditLogEntry` (уже есть в схеме) + уведомление ответственным (снабженец, если менялась норма расхода материала).

## 3. Схема БД (дополнение к уже присланной Prisma-схеме)

Прежняя `schema.prisma` уже покрывает ядро: `Article`, `Material`, `BomItem`, `Order/OrderLine`, `ProductionPlanItem`, `MinStockLevel`, `PurchaseRequest`, `PriceHistory`, `FinishedGoodsMovement`, `MaterialStockMovement`, `Employee`, `WorkCalendarDay`, `AuditLogEntry`. По итогам анализа Excel — **это верное соответствие** листам `Артикулы→Article`, `База сырья→Material`, `Спецификации 2022→BomItem`, `План→ProductionPlanItem`, `Минимальные остатки→MinStockLevel`, `На закуп→PurchaseRequest`, `Приход ГП/Склад ГП→FinishedGoodsMovement`, `Прайс→PriceHistory`.

**Пробелы, не покрытые текущей схемой:**

```prisma
// Лист "ЗП сотр." + "Рабочее время" + "Годовое время"
model LaborRate {
  id            String   @id @default(uuid()) @db.Uuid
  employeeId    String?  @db.Uuid @map("employee_id")
  hourlyRate    Decimal  @db.Decimal(10,2) @map("hourly_rate") // = 'ЗП сотр.'!N9
  validFrom     DateTime @db.Date @map("valid_from")
  employee      Employee? @relation(fields: [employeeId], references: [id])
  @@map("labor_rates")
}

// Лист "Telecom" / "Др проекты" — сделки/дебиторка
model Deal {
  id              String   @id @default(uuid()) @db.Uuid
  customerId      String   @db.Uuid @map("customer_id")
  articleId       String?  @db.Uuid @map("article_id")
  qtyOrdered      Decimal  @db.Decimal(12,2) @map("qty_ordered")
  qtyShipped      Decimal  @default(0) @db.Decimal(12,2) @map("qty_shipped")
  isPaid          Boolean  @default(false) @map("is_paid") // = столбец BK "Да/Нет"
  period          String?  @db.VarChar(10) // = 'Telecom'!AT
  customer        Customer @relation(fields: [customerId], references: [id])
  article         Article? @relation(fields: [articleId], references: [id])
  @@map("deals")
}

// Производный агрегат "Долги по отгрузкам" — можно как VIEW, не таблица
// SELECT customer_id, SUM(qty_ordered-qty_shipped)*price ... GROUP BY customer_id, is_paid
```

**Рекомендация:** `На закуп`, `Долги по отгрузкам`, месячные/недельные субтоталы `План`/`Склад ГП` — реализовать как **SQL VIEW / materialized view**, не как хранимые "calculated fields", синхронизируемые вручную сервисом (текущий риск рассинхрона уже отмечен в предыдущем разборе Prisma-схемы).

## 4. Ролевая модель (RBAC)

| Роль | Пишет | Читает | Утверждает |
|---|---|---|---|
| **Технолог** | `BomItem` (состав, нормы расхода, трудозатраты), `Article.weightKg` | `Material` (справочно) | — |
| **Снабженец** | `Material.purchasePrice`, `MaterialStockMovement` (приход), статус `PurchaseRequest` | `BomItem`, `ProductionPlanItem` (для расчёта потребности) | `PurchaseRequest.ORDERED` |
| **Начальник производства** | `ProductionPlanItem` (План), `ProductionStage` (этапы) | всё по цепочке производства | закрытие этапов |
| **Менеджер продаж** | `Order`, `OrderLine`, `Deal`, `Customer` | `Article`/`Прайс` (только УТВ цена, не себестоимость) | — |
| **Финансист/Руководитель** | `Article.approvedPrice` (УТВ цена) | всё, включая себестоимость и маржу | Approve цены, Approve крупных `PurchaseRequest` |
| **HR/Кадровик** | `Employee`, `LaborRate`, `WorkCalendarDay` | — | — |
| **Admin** | `User`, `Role`, `UserRole` | всё | — |

Колоночный уровень (пример: лист `Прайс`) — менеджер продаж видит `УТВ цена`, но не видит `Цена специф.`/себестоимость/маржу (сейчас в Excel всё в одном листе без разделения доступа — это прямая утечка себестоимости всем, у кого есть ссылка на файл, как видно из листа `Permissions`, где просто список email без ролей).

## 5. Roadmap (для Cursor)

1. **DB:** доработать `schema.prisma` — добавить `LaborRate`, `Deal`, версии `BomItem` (`validFrom/validTo`); прогнать `prisma migrate dev`; перенести агрегатные листы (`На закуп`, `Долги по отгрузкам`) в SQL views.
2. **Импорт данных:** написать one-off скрипт на базе уже существующего `SpreadsheetImport/Sheet/Row` стейджинга — замэппить 44 листа на целевые таблицы по ключам из раздела 1.2 (Артикул/Наименование), не через живые формулы, а через явный ETL с логом расхождений (`LogErrors`/`Log` уже есть аналоги в исходнике).
3. **Backend API:** REST/GraphQL эндпоинты по модулям — `/articles`, `/bom`, `/production-plan`, `/min-stock`, `/purchase-requests`, `/deals`; вычисляемые поля (Себестоимость, Готовность %, Нужно изготовить) — считать в сервисном слое или SQL view, не хранить дублем без триггера пересчёта.
4. **Frontend:** grid-компонент (AG Grid) с pinned-агрегатами, inline-редактированием только editable-колонок, autocomplete по справочникам вместо `Тех-лист`-костыля; realtime — WebSocket + optimistic locking по строке (article/BOM item).
5. **Workflow:** approval-стейт для `Article.approvedPrice` и `PurchaseRequest` (draft→pending→approved), уведомления (Telegram, т.к. в схеме уже есть `Employee.telegramId`) при изменении BOM/цены, влияющем на активные заказы.
